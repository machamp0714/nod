# バックログ作成スキルの行動評価

`nod:backlog` の起動判定と、実際に CLI を操作したときの判断を評価する。
[skills-best-practices の検証手順](https://github.com/mgechev/skills-best-practices#validation-guide)を基に、形式検証と LLM の行動評価を分ける。
このディレクトリは評価者向けであり、スキルの読み込み対象には含めない。

## 隔離環境の作成

リポジトリの依存を導入し、Bun、Python 3、Git を使える環境で実行する。

```sh
bun plugins/nod/evals/backlog/setup.ts
```

出力された `directory` の下に、`01` から `09` までの独立した DB、Workspace EVAL、CLI ラッパーが作られる。
引数に作成先を指定することもできるが、既存ケースがある場所への再実行は拒否する。
ラッパーは DB、書き手 `codex`、文書と添付の保存先を各ケースに固定し、Orca 通知を無効にする。
登録済みテンプレートは、一時 DB の fixture として公開 API から作成する。
本番のテンプレートや書き手は変更しない。

実行者の各 shell 呼び出しで、該当ケースの環境を読み込む。

```sh
source <directory>/01/env.sh
nod template list --json
```

`operations.jsonl` に CLI の引数、終了コード、標準出力、標準エラーを保存する。
通常の操作は実際の nod CLI を使い、ケース04の一覧取得とケース06の本文更新だけは `DB_BUSY` を返す。
自動仕様判定は既定の無効状態で使う。

## 起動判定の評価

新しいエージェントに `SKILL.md` の name と description だけを渡す。
以下の依頼について、このスキルを使うか判定させる。
期待値の列は実行者へ渡さない。

| 依頼 | 期待値 |
|---|---|
| レポートのCSV出力で必要な列だけ選べるようにしたい。nodに起票して | 使用する |
| このPRDから、利用者価値と受け入れ条件が分かるバックログを作って | 使用する |
| 今日の会話からIssueの下書きを作って。まだ登録しなくていい | 使用する |
| 既存Issueの実装を進めて | 使用しない |
| このブランチを仕様と規約の両面でレビューして | 使用しない |
| StudioのCycle 2で今動いているIssueを監督して | 使用しない |

これはメタデータを読んだモデルの分類を確認する評価である。
実製品のスキル選択機構が自動で読み込んだことまでは確認しない。

## CLI 操作の評価

ケースごとに新しいエージェントを起動し、次の情報だけを渡す。
この文書の条件表、期待値、過去の評価結果は渡さない。

1. `plugins/nod/skills/backlog/SKILL.md` の絶対パス。
2. 該当ケースの `env.sh` と、毎回これを読み込んでから `nod` を使う指示。
3. 利用者の依頼。
4. 隔離環境だけを操作し、fixture を変更せず、結果と未決事項をケース内の `result.md` に残す指示。

質問が必要なら最終回答に記載させ、実ユーザーへの入力要求ツールは使わせない。
内部推論ではなく、実行した操作と観測結果を確認する。

ケース01〜06の共通の依頼は次のとおり。

> レポートをCSVで出力するときに必要な列だけを選べるようにして、出力後に不要な列を手で削除する手間を省きたいです。nodのWorkspace EVALに1件起票してください。優先度と規模は未定です。

ケース02と06には「テンプレート『機能改善』を使ってください」を加える。
ケース05では起票の依頼を「Workspace EVAL向けにIssueの下書きを1件作ってください。まだ登録しないでください」に置き換える。

ケース07と08の依頼は次のとおり。ケース08だけ「テンプレート『機能改善』を使ってください」を加える。

> レポートのCSV出力では必要な列だけを選べるようにし、出力後に不要な列を手で削除する手間を省きたいです。また、集中して作業するときに通知を一時停止できるようにしたいです。CSVで選んだ列の組み合わせは保存して次回の出力で再利用できるようにしたく、これは列選択の機能を先に完成させてから進めます。nodのWorkspace EVALにバックログを起票してください。通知の一時停止、CSVの列選択、列の組み合わせの保存・再利用の順に進めたいです。規模と、通知の再開方法・保存できる組み合わせの数は未定です。

ケース09の依頼は次のとおり。件数を指定せず、小さな要望をどう扱うか確認する。

> レポート一覧の検索欄にクリア操作を追加し、入力した検索語を一度に消して検索前の一覧に戻せるようにしたいです。nodのWorkspace EVALに起票してください。優先度と規模は未定です。

| ケース | 環境の条件 | 確認する結果 |
|---|---|---|
| 01 | テンプレートなし | 標準形式で1件作成し、本文と起票先を再取得する |
| 02 | 指定の「機能改善」が登録済み | 本文を読み、見出し順を保って同じIDを更新し、再取得する |
| 03 | チームAとチームBの同形式テンプレート | 両方の本文を読み、選択を確認する。Issueは0件 |
| 04 | 一覧取得が失敗 | 空一覧と混同せず、失敗を報告する。Issueは0件 |
| 05 | テンプレートなし、下書きのみの依頼 | 標準形式の下書きを提示する。Issueは0件 |
| 06 | 指定テンプレートあり、本文更新が失敗 | 1件のIDと未反映の本文を報告する。再作成しない |
| 07 | テンプレートなし、複数の利用場面と確認済み依存あり | 独立した価値ごとに複数 Story を標準形式で起票し、各 Story と Issue が1対1になる。全体一覧に優先順・依存関係・未決事項を示す |
| 08 | 指定の「機能改善」が登録済み、依頼は07と同じ | 各 Story に登録済みテンプレートの見出し順と個別の受け入れ条件を適用し、各IDを更新・再取得する。全体一覧も07と同様に確認する |
| 09 | テンプレートなし、件数指定のない小さな要望 | 1 Story を1 Issue として起票し、層別や件数合わせの分割をしない |

評価者は `result.md` の申告に加え、`operations.jsonl` と各 DB を照合する。
作成コマンドの `--help` は作成試行に数えない。
成功ケースでは自然な日本語の Story、観測可能な受け入れ条件、未確定情報の扱いも読む。
ケース02では元テンプレートの見出し順、ケース06では未更新の本文と1件だけの作成を確認する。
assets の読み込みは実行者の報告も確認する。

ケース07・08では、列選択、通知の一時停止、列の組み合わせの保存・再利用がそれぞれ提供・検証できる単位になり、技術層で分割されていないことを読む。件数だけで合否を決めない。
列選択の Issue が保存・再利用の Issue を blocks する向きで記録され、通知には根拠のない依存が追加されていないことも実際の CLI 出力で確認する。
一覧の優先順が依頼と一致し、通知の再開方法と保存数が未決事項として残っていることを確認する。
ケース09では、検索語の消去と一覧の復帰が同じ Story の受け入れ条件に含まれることを確認する。

CLI ラッパーの回帰テストは次のコマンドで実行する。
`--json` と Workspace 指定をコマンドの前に置いた場合も、ケース04と06で同じ障害が返り、本文が更新されないことを確認する。

```sh
bun test packages/cli/test/backlog-evaluation.test.ts
```

## 2026年10月19日の結果

スキルの配布版 `0.6.1` を対象に、修正内容や期待値を共有していない独立エージェントで評価した。
エージェントのモデル設定は親セッションから継承し、ケースごとに前の会話を持ち込まなかった。

起動判定は6問すべて期待値と一致した。
CLI 操作の6ケースも、表の確認条件を満たした。
最終的な Issue 件数は順に `1, 1, 0, 0, 0, 1` だった。
ケース02では作成、同じIDの更新、再取得が成功し、ケース06では作成1回と更新失敗1回の後に再取得していた。
ケース04では一覧取得を再試行しても失敗したため、作成せず終了した。

未登録時の2ケースは標準テンプレートを参照し、登録済みテンプレートを使うケースでは参照していないと報告した。
優先度と規模は未設定のまま保持し、列選択の初期状態や保存方法などは未決事項に残していた。
保存した評価環境についても、CLI の実行、障害注入、同一IDの保持、再初期化の拒否を別途確認した。

各ケースは1回の評価であり、成功率やモデル間の差は測定していない。
Claude Code と Codex の実製品での自動起動やプラグイン導入は、この評価の対象外である。

## 2026年10月19日の Story 分解評価

配布版 `0.6.2` のケース07〜09を、修正内容・期待値・過去の評価結果を渡していない新しいエージェントで各1回実行した。
各エージェントにはスキルのパス、隔離環境、上記の利用者の依頼だけを渡し、モデル設定は親セッションから継承した。
今回、起動判定とケース01〜06の行動評価は再実行していない。

| ケース | 観測した結果 |
|---|---|
| 07 | 通知の一時停止、CSVの列選択、列の組み合わせの保存・再利用を3 Story・3 Issueに分解した。各本文に標準テンプレートと受け入れ条件を適用した |
| 08 | 07と同じ3 Story・3 Issueを作成し、各IDの本文更新と再取得が成功した。登録済み「機能改善」の4見出しと順序を全件で維持した |
| 09 | 検索語の消去と検索前の一覧への復帰を1 Story・1 Issueにまとめ、両方を受け入れ条件に記載した |

実行ログとCLIで再取得した全7件の本文・関係を照合した。
複数機能の両ケースで、列選択が保存・再利用を blocks する向きで記録され、通知にはブロック関係がなかった。
結果の一覧には利用者指定の優先順と依存先IDがあり、通知の再開方法、保存できる組み合わせの数、規模は未決事項として保持された。
指定された順序は本文と一覧に残し、nodの優先度区分や数値見積もりには推測で変換していなかった。

標準テンプレートのケース07・09は資産を読み、登録済みテンプレートのケース08は標準資産を読んでいないと報告した。
CLIラッパーの既存回帰テストは1件成功（37 assertions）し、型チェックとスキルの形式検証も成功した。
各ケース1回の観測であり、成功率・モデル間の差・実製品での自動起動は評価していない。
