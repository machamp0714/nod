# nod での記録・状態管理

## 親子と依存

コマンドの細部は実行環境の `--help` で確認する。
引数はシェルとして安全に渡し、Markdown の改行を保つ。長文は一時入力ファイルや標準入力対応のコマンドを使い、文字列のシェル展開を避ける。

```sh
nod issue create "<マップのタイトル>" -d "<マップ本文>" -l wayfinder:map
nod issue create "<判断のタイトル>" -d "<問い>" --parent <マップID> -l wayfinder:grilling
nod issue relate <先に解決する子ID> --blocks <後から進める子ID>
nod issue show <マップID> --json
```

Project が指定されていれば create に `--project <Project>` を添える。
Project 作成を依頼されたら、同名がないか `nod project list --json` で確認し、`nod project create` で作る。
既存のマップを移すときは親だけでなく全ての子にも設定し、紐付け後に件数を確認する。
ユーザーが指定していない Project を推測して作らない。

## 起票とラベル

自分で付ける分類は、親の `wayfinder:map` と子の型ラベル一つだけにする。
nod が自動で付けた `needs-spec` や人が付けたラベルは保持する。
これは元の wayfinder の「wayfinder ラベルだけ」を nod の運用へ適応するための例外である。
ラベルを揃えるために人の管理するラベルを削除したり、自動判定を無効にしたりしない。

起票した Issue は Triage に入る。
親子・依存・本文を作って内容を見せたうえで、受理が必要な Issue をまとめて案内する。
`nod triage accept`・却下・重複判断・レビュー承認は人が行う。
既に受理されていれば再度求めない。会話上の賛同と nod 上の状態遷移は別なので、操作結果を読む。

## 着手できる子を選ぶ

`nod issue show <マップID> --json` の `children` で親子関係を確認し、次を突き合わせる。

```sh
nod issue list --ready --assignee none --sort id --json
```

ready 一覧をそのまま使わず、指定マップの子だけに絞る。
未受理・承認待ち・他担当・スヌーズ中の子を候補にしない。
指定した子の `start` 直前にも状態を確認する。担当は `start` 成功によって確保し、事前の `update --assignee` で他の担当を上書きしない。
`start` が競合や制限を返したら手引きに従う。全体から選び直すときもマップ配下に限定する。

仕様判定が pending・failed で着手を制限している場合は `nod issue assess <id>` を一度だけ再試行し、回復しなければ理由を報告する。
`needs-spec` は実装可否の目印であり、このスキルは仕様を決めるための検討である。ラベルを消して実装を始めない。
検討への着手も CLI が拒否した場合は、状態・書き手・DB を変えて回避しない。

`blockedBy` がないだけで回答済みとは見なさない。
前提が canceled・アーカイブ扱いになったときは、到達点の変更・問いの無効化なのかを確認する。
前提の答えが不要になった理由が確認できるまでは、それを決定済みとして後続の判断材料にしない。

## 回答から承認まで

```sh
nod issue comment <子ID> "<解決コメント>"
nod issue done <子ID> --summary "<回答の要旨と根拠資料>"
```

解決コメントには次を記録する。

- 問いへの回答と理由。
- 人の判断が必要な型では、合意した内容と対話記録 Document。
- 調査・試作などの根拠資料へのリンク、未検証事項や適用条件。
- 新しく生まれた問いがあれば、その子 Issue へのリンク。

`issue done` は in_review への提出であり、done への確定ではない。
既に提出済みなら再提出せず承認結果を確認する。
人の承認前はブロックを残す。承認後に done を再取得して、親の索引へ反映する。
差し戻しは理由を読み、同じ子の回答を修正して再提出する。

対象外・重複・無効化した子は、理由をコメントし人に中止や整理を依頼する。
依存を都合よく外して着手する操作はしない。

## マップ本文の並行更新

子の結果は各担当が自分の子に記録し、親本文の索引はマップの主担当一人が更新する。
別セッションと主担当が競合している場合は、親へのコメントに追加予定の要旨と子のリンクを残し、本文統合を主担当に委ねる。

更新担当は直前に親本文を再取得し、既存の記述を保った最小の追記を作る。
更新後も再取得して他の追記を消していないか確認する。
nod の本文更新に条件付き更新はないため、再取得だけで同時更新を防げるとは説明しない。
競合を検知したら更新を繰り返さず、子の正本と Activity の記録を保って統合を相談する。

承認前の回答を決定済み索引に入れない。
未承認の結果を探す際は子の状態と Activity を読み、親本文に別の回答一覧を増やさない。
