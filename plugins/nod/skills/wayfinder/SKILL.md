# nod:wayfinder

大きな構想について、実装前に決めるべきことを **判断用 Issue** に分け、人との対話を通して進める。
親 Issue が全体のマップ、子 Issue が一つずつの問いとなる。
成果は判断とその根拠であり、通常は実装やデプロイまで進めない。

## 呼び出しと準備

- 新規: `nod:wayfinder <構想>`。任意で既存 Project を指定する。
- 再開: `nod:wayfinder <マップの Issue ID>`。子 Issue ID も指定でき、省略時は次の候補を選ぶ。
- 子 Issue だけを指定された場合は `parentId` からマップを確認する。マップでない親を勝手に作り変えない。
- 別モデルの指定は `nod:to-spec` と同じく `--reviewer-model`、`--reviewer-effort` を受け付ける。これらはスキルへの指示であり、nod CLI のオプションではない。

Codex では nod を書き換える前に `export NOD_ACTOR=codex` を設定する。
`nod skills get nod` と [nod での記録・状態管理](references/nod-operations.md) を読む。
既存の本文・合意・Documents を前提にし、変更したい場合は変更提案として人に示す。
用語は `CONTEXT.md` や既存の用語集に合わせる。
利用可能なら grilling・domain-modeling を使う。未導入でも、以下の対話手順を実行できる。

## 対話と正本

- **対話はこのスキルに含まれる。** 判断用 Issue ごとに `nod:to-spec` を別途呼ぶ必要はない。
- 判断を人に代わって確定しない。別モデルとの一致は推奨の根拠であり、ユーザーの回答ではない。`nod:to-spec` の「一致なら確定」はこのスキルには引き継がない。
- 同じセッションでは判断用 Issue を一件だけ解決する。独立した research は複数扱ってよい。新規マップを作る回は、到達点と全体の境界を揃え、子の判断には踏み込まない。
- 人に示す参照は Issue のタイトルで書く。リンクの中に ID を含めてよいが、裸の番号を並べない。
- 最終回答の正本は子 Issue の解決コメント。議論の経緯と照合結果はその子の Document、試作や調査資料はリンクする資料に置く。親には一行の要旨と子へのリンクだけを残す。
- 利用者に聞くのは選択・優先順位・許容範囲。コードや資料から分かる事実は自分で調べる。

## 新規マップを作る

1. **到達点を人と決める。** 何を決め終えたら実装に渡せるか、誰のどんな利用を扱うかを問い、推奨案を添える。既に回答されたことは聞き直さない。
2. **幅を広げて未決事項を探す。** 特定の実装方式に深掘りする前に、範囲・互換性・運用などの独立した論点を一巡する。前提が未決の質問は次のラウンドに回す。具体的な対話と記録は後述の手順に従う。
3. 一回で全て決められる小さな仕事なら、マップを量産せず、通常の仕様検討へ進める案を示す。
4. 下の形で `wayfinder:map` の親 Issue を作る。会話記録の Document をリンクする。Project を指定された場合は親子とも同じ Project に入れる。既存マップを再利用できるか、起票前に検索する。
5. **今、問いを明確に書けるものだけ**を子 Issue にする。答えをまだ出せなくても、問いが明確なら依存付きの子にする。問い自体がまだ曖昧な領域は「まだ具体化できない事項」に残す。
6. 全ての子を作って実 ID を得てから `blocks` を設定する。本文の相互参照もこの時点で実際のリンクを使う。
7. 親子・ラベル・依存の向きと循環の有無を確認する。研究は受理済みで着手条件を満たすものだけ担当を確保して委任する。未受理なら具体的なマップを示し、人に受理を依頼する。新規起票直後の研究を自動着手しない。

親 Issue の本文:

```markdown
## 到達点

このマップで何を決め終えるか。

## 進め方と前提

合意済みの範囲、参照するスキル、Project、並行作業時の索引更新担当。
通常は計画まで。実行も扱う場合は、人が指定した範囲を明記する。

## 決定済み事項への索引

初回は空。承認済みの子のタイトルへのリンクと、一行の要旨だけを記録する。

## まだ具体化できない事項

到達点の範囲内で、まだ問いを明確にできない領域。

## 対象外

今回扱わないことと、その理由。
```

未完了の子の一覧は親本文に複製せず、nod の親子関係から取得する。
初期合意は「進め方と前提」に置き、未解決の子を決定済みとして索引に載せない。

## マップを再開する

1. 親の到達点・前提と子の状態を読む。既に done になった子の索引が未反映なら先に同期する。全子の本文を先読みせず、今回必要な根拠だけを読む。
2. 子の指定がなければ、マップ配下の **受理済み・着手可能・未担当・有効なブロック元なし** の子から ID 昇順で一件選ぶ。`in_review` は未完了。他担当や別セッションで作業中の子を奪わない。マップ外も選ぶ `nod issue next` は使わない。
3. `nod issue show <子ID> --json` で本文・型ラベル・判定状態を読み、`nod issue start <子ID>` が成功して担当を確保してから着手する。指定された子でも制限を迂回しない。自分の中断作業を再開する場合は Activity と作業場所を照合する。
4. 下の型に沿って一件を進める。今回の判断と関係しない未決事項が見つかれば、問いを切り出して深追いしない。
5. 回答・根拠・人との合意を解決コメントに記録し、`nod issue done` でレビューへ提出する。人が承認して done になるまでは、後続の依存を解除せず、決定済み索引に加えない。
6. 新しく明確になった問いを子にし、依存を設定して対応する「まだ具体化できない事項」を除く。対象外と判明した子は理由をコメントし、人に中止を依頼する。中止後は「対象外」にリンクし、「決定済み事項への索引」には入れない。
7. 未完了の子・未整理の領域・承認待ちがなく、到達点を満たせば親をレビューへ提出する。親が todo なら状態を確認して `nod issue start <マップID>` に成功した後、`nod issue done` で提出する。人の承認まではマップ完了と報告しない。まだ残るなら、次に扱える判断か必要な人の操作をタイトル付きで示して終える。

## 子 Issue の型

本文は `## 問い` から始め、その子で何を明らかにするかを書く。
型は本文から推測せず、次のラベルで判定する。

| ラベル | 進め方 | 回答に必要なもの |
| --- | --- | --- |
| `wayfinder:research` | エージェントが一次資料とコードを調べる。独立した問いは別のサブエージェントへ委任できる。 | 出典、確認できた事実、推論、未検証事項を分けた報告。採用判断を代行しない。 |
| `wayfinder:grilling` | 以下のラウンド制で人と対話する。 | ユーザーが確認した判断と根拠。 |
| `wayfinder:prototype` | 判断したい点に絞った小さな試作品を作り、人に操作や挙動を確認してもらう。 | 試作品へのリンク、確認結果、人の反応を受けた判断。 |
| `wayfinder:task` | 判断に必要な準備作業を行う。人にしかできない部分は具体的な手順を示す。 | 実施内容、確認できた事実、残る制限。目的の実装を紛れ込ませない。 |

research の資料は nod の Document に保存する。
研究用ブランチが必要な場合は `research/<内容>` に分離し、公開が認められた範囲だけを push する。公開はスキル呼び出しだけでは必須にせず、PR・マージもしない。
サブエージェントが使えなければ同じ調査を順に進める。
研究担当は資料と回答を作り、親マップの索引更新は一人の担当に集約する。

## 対話の一ラウンド

`nod:to-spec` を参考に、別モデルによる独立照合と永続的な記録を行う。
初回の対話前に [対話と照合の記録](references/dialogue.md) を読み、nod の Document を用意する。

1. 前提が決まっている問いだけを集め、自分の推奨・理由・根拠を先に記録する。
2. 自分の推奨を伏せた問いと確定済みの前提を別モデルに渡す。返された事実は確認してから用いる。
3. **一致した問いも含め、人に質問と推奨を示す。** 不一致は両案と根拠を添える。「はい」で推奨案を採用できる形にし、短い回答やまとめての回答を受け付ける。
4. 回答を待ち、質問・推奨・独立回答・ユーザー回答・決定を Document に追記する。回答前に確定扱いにしない。
5. 回答によって新たに問える論点を次のラウンドにする。残る問いがなくなったら合意内容をまとめ、人が確認した時点でその判断をレビュー提出できる。

チャットで対話が続いている間は、同じ質問を `nod issue ask` に重複登録しない。
中断して人の回答待ちを永続化する場合は `ask` を使い、既存の未回答を再利用する。
人が登録した未決事項には代理回答しない。

## 実装へ渡すとき

マップは実装タスク一覧ではない。
全ての判断が揃ったら、決定済みの子を根拠に実装対象の Issue を作る、または既存 Issue に引き渡す。
仕様が不足する対象には `nod:to-spec`、仕様から実装計画を作る対象には `nod:to-plan` を使う。
判断用の子を一律に `to-spec` にかけたり、`ready-for-agent` を付けたりしない。
実装開始やリリースは、ユーザーが求めた次の作業として扱う。
