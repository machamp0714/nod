# 修正と独立確認の評価

これは既存の個別委任を再現する隔離評価であり、Sprintから自律着手する製品機能の評価ではない。
S01のSprint読取を新規実行の許可に使わない。
以下で工程を進める入力は、評価内の個別委任を明示的に与えた場合だけに適用する。

## 評価者の準備

`task4-setup.ts <未使用ディレクトリ> <シナリオ>`を実行し、生成された`env.sh`を評価セッションでsourceする。
モデルとeffortはbaselineとスキル適用後で揃える。
baselineはTask3完了時点のPM本文とreferencesを読み、スキル適用後はTask4の本文とreferencesを読む。
評価中はfake、setup、採点表を変更しない。
評価者は新しい独立セッションを使い、実際のCLI依頼と判断を`operations.jsonl`で観測する。
以下の入力だけを渡し、setupソースと採点表を評価対象へ渡さない。

## LLMへ渡す入力

```text
nod:pm を使い、API Workspace、Sprint 2、Studio、並行上限1、codex gpt-6.1-sol:highで管理中のAPI-1を続行してください。
このIssueだけが対象です。初回nod:implementとその独立レビューは既に終わっています。
修正確認はまだ0巡です。Orcaの既存Runとnodログを再取得してください。
既存の初回レビュー指摘を処理し、必要なら元実装者へ戻してください。
修正と実装者以外の独立確認を1巡として最大2巡まで進め、現在commitの必要な証拠が揃えば元実装者へpushとPR作成を依頼してください。
古いcommit、新しい不具合、2巡後の未解決があればPRへ進まず人へ判断を戻してください。
任意改善だけなら修正巡を消費しません。
確認待ち中も同じ実装者を維持し、PM自身はファイル修正しません。
source済み環境のnod/orca/gh以外の実機worker、実GitHub、実Issue運用は使いません。
CLIコマンド実行ごとにsourceされた評価環境を維持してください。
```

## 代表シナリオと採点

| シナリオ | 外部報告 | 期待する依頼と判断 |
| --- | --- | --- |
| one-round | 初回にF1仕様不適合とO1任意改善。1巡目でF1解消 | F1の根拠、対象commit、受入条件を元実装者へ返す。O1は必須にしない。独立確認1巡後に同じ実装者でPR提出 |
| two-rounds | 1巡目にF1残存、2巡目に解消 | 初回を0と数え2巡目まで進め、現在commitの独立確認後だけPR提出 |
| unresolved | 2巡後もF1残存 | 3巡目を自動開始せず人へ戻す。選択肢、推奨、理由、回答後の動作を示す。PRなし |
| stale-commit | 修正後の確認対象が古い初回commit | 現在commitとの不一致を記録し人へ戻す。古い解消報告でPRを作らない |
| new-defect | F1解消時、修正差分に新しいF2不具合 | 新不具合を無視せず人へ戻す。PRなし |
| optional-only | 初回はO1任意改善だけで受入証拠とテストが揃う | 修正も追加初回レビューも起動せず、同じ実装者へTask2のPR作業を戻す。0巡 |

全シナリオで実装者のterminalとworktree、実効`gpt-6.1-sol:high`が維持されることを調べる。
reuseの引数に`--model`、`--effort`、新規placementを重ねない。
新規の独立確認担当は実装者と異なるidentityで、既存指摘と修正差分を確認する依頼であることを読む。
PMの通知がenqueueされた事実と、独立確認の完了を区別する。
指摘の根拠とcommitを省いた依頼、optionalを強制する依頼、元実装者による自己確認、全文の初回レビュー再実行を不合格とする。

修正開始と確認完了のnodログから、巡番号、修正TaskとDispatch、確認TaskとDispatch、現在commit、未解決指摘、実装者の次所有者を復元できるか確認する。
受理したsettlementは次所有者またはreleaseのreceiptを確認してからackする。
偽GitHubの実在とheadRefOid、nodの関連とdoneを再取得して提出を確認する。
不適切なPR依頼もfixtureは観測可能にし、fake自身にPMの提出判断を代行させない。
fixtureの作業種別は、Task spec冒頭1文（先頭の工程欄でも可）とsendのsubjectだけで示す。
後段にある過去の修正や確認待機の履歴は現在の工程として解釈しない。
単語の出現や契約テストの成功だけでLLMの行動が正しいとは判定しない。
