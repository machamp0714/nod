# nod:pm

指定したWorkspaceと固定CycleのIssueを管理する。
PMは要求の確認、依頼、結果の照合、人への相談を担当し、実装ファイルは実装担当が変更する。
要求と判断の正本はnod、実行の権限と状態の正本はOrcaのRun、Task、Dispatchである。
以前の会話だけに依存して担当や工程を決めない。

## 1. 起動条件を揃える

呼び出し例:

```text
nod:pm API --cycle 2 --on Studio --max-parallel 2 --agent codex --model gpt-6.1-sol --effort high
```

これらはスキルへの指示であり、`nod` CLIのサブコマンドやオプションではない。
自然文の指定も同じ入力として扱う。
例のモデルを既定値にしない。

作業開始前に、次の入力を具体的な値として揃える。
既に指定、合意された値は聞き直さない。

| 入力 | 確認する値 |
| --- | --- |
| Workspace | 登録済みのキーとパス。複数Workspaceへ広げない |
| Cycle | IDと名前。`current`や名前は起動時にIDへ一度解決し、以後は固定IDを使う |
| 実行先 | Studioの接続先と対象リポジトリ。PMの入口はAir。Airへ黙って切り替えない |
| 並行上限 | 省略時1件、明示時1または2件。0、3以上、整数以外を受け入れない |
| 実装担当 | CodexまたはClaude Codeと、nodで使う担当名（`codex`または`claude-code`） |
| モデルとeffort | 個別のユーザー指定、または起動時に合意した許可組み合わせと選定方針 |

モデルは個別指定を最優先にする。
指定や合意済み方針がなければ、既存のユーザー設定を調べ、具体的なモデルIDとeffortとして確認する。
値が不明、非対応、許可された範囲で実行できない場合は、必要な値と理由を人へ確認する。
無回答や時間経過で確定しない。
人への確認は[質問の手順](references/questions.md)に従い、番号選択肢、推奨、理由、決定後の動作を示す。
依頼ごとに`モデル:effort`と、複雑さ、影響範囲、検証の難しさを根拠とした選定理由を提示する。
要求値を書いただけでは適用確認とせず、新規依頼時は実行先の対応とOrcaの`launch.requested`、`launch.effective`を確認してから実装を始める。

Codexではnodへ書き込む前に`export NOD_ACTOR=codex`を設定する。
`nod skills get nod`と、この環境の`orchestration`スキルを読み、そこで解決したOrca実行ファイルを以後も使う。
Orcaの実行ファイルから`skills get orchestration`で現行の手引きを取得する。
未対応の操作やflagを推測しない。
この節の入力を短く提示し、以後は指定Workspaceと固定Cycleだけを再取得する。

## 2. 候補と既存実行を照合する

最初の選定と新規着手直前に、[候補の確認手順](references/candidates.md)を使う。
一覧の`--ready`だけで実装可能と判断せず、本文、担当、依存、質問、仕様判定、既存実行を照合する。
人や他担当の作業、管理外の既存セッション、未受理のTriageを引き取らない。
通信断や読み取り失敗は`unverifiable`として扱い、生存不明のworkerを失敗や終了と推定しない。

並行上限に数えるのは、このPMが管理する実装Issueの枠である。
実装開始からPR提出または人への明示的引き継ぎまで1枠を占有し、レビュー中、指摘対応中、人の回答待ちも同じ枠に含める。
仕様準備のIssue数と実装Issue枠を区別する。
管理外のworkerは、対象Issueへの二重着手を防ぐために照合する。
そのworkerの数をPMの枠に加算したり、空き枠を作るために終了させたりしない。
例えば上限2件、PM管理内0件、管理外worker1件ならPMの空き枠は2件である。
別途、候補同士と既存作業の変更範囲が競合しないか確認する。

## 3. 候補と待機理由を提示する

報告は、起動条件、PM管理内の占有枠と空き枠、Issueごとの分類、理由と次の条件の順に書く。
分類は「実装可能」「仕様準備」「人への確認待ち」「依存待ち」「管理外」を使い、複数の停止理由があれば併記する。
管理中の既存作業は新規候補に混ぜず、工程と実行の対応を示す。
指定外Workspace、次Cycle、Cycle未設定のIssueを新規候補へ入れない。
Cycle内の変更は固定IDで再取得するが、次のCycleへ自動で管理範囲を広げない。

候補表示だけを依頼された場合は、この報告で止める。
候補を見せるためにRun、Task、Dispatch、worker、PRを作らず、`nod issue start`や着手を伴う`next`も使わない。
初回仕様判定の1回の回復と停止理由の記録は、確認手順に従う。
人だけが行えるTriage判断、最終レビュー承認、マージ、本番反映を代行しない。

## 4. 1件を実装からPR提出へ進める

実装まで依頼されている場合は、[実装依頼と提出の手順](references/implementation.md)を使う。
新規着手直前に候補と空き枠を再確認し、Studioの専用worktreeで実装者を起動する。
初期依頼には「PMが`launch.requested`と`launch.effective`を照合して開始を通知するまで、実装も`nod issue start`も行わない」という開始条件を入れる。
Studioの対応を確認し、起動結果が指定と一致した場合だけDispatch宛てに開始通知を送る。
非対応、不一致、実効値不明なら、そのIssueを停止して理由と既存実行を残す。

実装者の報告では、現在commitに対応する受け入れ証拠、必要なテスト、初回独立レビューのStandardsとSpecを揃える。
`nod:implement`には初回レビューが含まれるため、PMから同じ初回レビューを二重起動しない。
指摘なしで証跡が一致したら、同じ実装者と実効設定を維持してpushとPR作成を依頼する。
必須指摘があれば[指摘修正と独立確認の手順](references/review-fixes.md)で元実装者へ戻す。
仕様不適合、規約違反、不具合と任意改善を分け、根拠、対象commit、受入条件を揃えて依頼する。
初回レビューを0とし、修正と独立確認を1巡として最大2巡まで進める。
確認対象は既存指摘と修正差分に絞り、実装者と異なるidentityで確認する。
現在commitの必要テストと指摘解消の証拠が揃った場合だけPR経路へ戻し、古いcommit、新しい不具合、上限後の未解決は人へ戻す。
任意改善だけで修正巡を消費せず、PM自身は修正しない。
PRの実在、対象commit、nodとの関連と`in_review`を確認して、人のレビュー待ちとして報告する。
PR作成のための追加承認は要求しない。

## 5. 仕様準備と質問待ちから元の作業へ戻す

needs-spec付きIssueは[仕様準備の手順](references/specification.md)で既存の`nod:to-spec`へ渡す。
別モデルとの照合、未決論点への実回答、仕様とテスト境界の合意、正式Specの添付を確認する。
needs-specの解除はto-specの正式な確認工程でのみ行い、既存の合意を聞き直して不要な承認を増やさない。
仕様準備中と人の回答待ちも、既存workerのcheckを続けて通知を処理する。

worker質問と全工程の人への相談は[質問の手順](references/questions.md)を使う。
本文、仕様、決定ログで回答できる技術質問は根拠を記録して元workerへ返し、新しい利用者判断だけ人へ戻す。
人にはIssueと質問ID、番号選択肢、推奨、理由、決定後の動作を示す。
チャットまたはnodの実回答を一意に対応させ、原文と出典をnodへ記録した後、同じ元作業へ渡す。
人起点質問をLLMが代理回答せず、回答先不明、曖昧な回答、無回答、経過時間では再開しない。
