# 質問の記録と元の作業の再開

人への確認が必要な全工程でこの手順を使う。
起動条件、モデルの非対応や不一致、仕様の論点、worker質問、提出停止の相談も同じ書式に揃える。
以下の`ORCA`は、このセッションで現行手引きを取得した実行ファイルを指す。
`references/messaging-and-gates.md`と必要な操作の`--help`を確認し、messageやDispatchのIDを推測しない。

## 質問の発生元と回答の根拠

Orcaの`check`でDeliveryを受け取り、全行のRun、Task、active Dispatch、Issueをnodの管理記録と照合する。
workerのblocking `ask`には元message IDへの`reply`が必要である。
`send`の成功だけで質問が解消したと扱わず、質問へ答えるためだけにTask DAGのgateを作らない。
古いDispatchの質問や対象不明の通知は照合が済むまで再開に使わない。

| 発生元と内容 | PMが行うこと |
| --- | --- |
| workerの技術質問で、既存本文、正式Spec、決定ログから答えが一意 | 該当する本文の項目、Document IDと節、既存決定を確認する。根拠と回答をnodへ記録し、元messageにreplyする。人へ既決事項を聞き直さない |
| worker質問で、新しい利用者判断が必要 | 新しい要件、費用、利用方法、既存の合意の変更をPMや別モデルの一致だけで決めず、次の書式で人へ質問する |
| 根拠が矛盾する、または読み取れない | 推測で技術回答にせず、不足する根拠を調べる。未決の利用者判断なら人へ戻す。通信断はunverifiableとして元作業を保持する |
| 人が起こしたnod質問（askedBy=me） | LLMによるanswerは禁止。実際のチャット回答があってもlogへの記録にとどめ、人自身のnod回答を案内する。書き手変更、DB操作、状態変更で制限を回避しない |

別モデルの独立回答は仕様の照合材料であり、人の回答原文ではない。
人が起こした質問の代理回答や、新しい利用者判断の承認に転用しない。

## 人に示す質問

質問する前に最新のIssueと未回答質問を読み、同じ未決事項の質問IDがあれば再利用する。
新しいPM起点質問は`nod issue ask`で作り、receiptの質問IDを取得する。
番号はIssue IDと質問IDに対応させ、複数Issueを同じ「質問1」だけで指さない。
一つの質問で決めることを一つに絞り、選択肢の意味が混ざらないようにする。

```text
対象: <IssueID> / nod質問#<質問ID>
確認すること: <未決事項>
1. <案1と選んだ場合の動作>
2. <案2と選んだ場合の動作>
推奨: <番号を1つ>。理由: <要求、制約、影響に基づく理由>
決定後: <どの元作業で何を再開するか>
回答方法: このIssueと質問番号に対してチャットで番号を答えるか、nodで当該質問へ回答する。
```

停止や設定不足の相談も、確認できた実行可能な選択肢だけを番号で示す。
例えば非対応モデルなら「1. 元設定が対応するまで停止（推奨）」「2. 利用者が対応確認済みの別設定を指定」とし、未確認の代替モデルを実行可能と提示しない。
推奨の選択や回答期限の到来を実回答に置き換えない。

```sh
nod -w <Workspace> issue ask <IssueID> "<質問、番号選択肢、推奨、理由、決定後の動作>" --json
nod -w <Workspace> issue log <IssueID> "<質問の対応と待機条件>" --kind blocker
```

ログには、質問ID、質問の原文、選択肢、推奨と理由、元の工程、Run、Task、Dispatch、workerの質問message ID、terminalとworktree、モデルとeffort、停止理由、再開条件を残す。
Orca質問がない起動前の確認では、未作成の実行IDを捏造せず「実行未作成」と書く。
人の回答待ちでも元の実装枠を占有し、workerを終了扱いにしたり新しい実装者を起動したりしない。

## 実回答の取り込み

チャットまたはnodから実回答を得たら、最新のIssue、質問、元の実行対応を再取得する。
Issue ID、質問ID、選択肢の対応と回答の意味が一意であることを確認する。
未回答質問が複数あるときの「それで」「2」、推奨への曖昧な相づち、回答先不明の発言を補わず、対象と選択を確認する。
「2。90日」の番号と説明が現在の選択肢に矛盾する場合も確認が必要である。
質問が一つでも、回答内容自体が曖昧なら再開しない。
無回答、checkのtimeout、時間経過、workerの推測は実回答にならない。

| 窓口 | nodへ残す原文と出典 |
| --- | --- |
| チャット | 利用者の回答原文を改変せず引用し、会話上の発言日時と取得できるメッセージ識別子、対象Issueと質問ID、対応する選択肢を記録する。識別子を取得できなければ実際に分かる日時と発言文を使い、存在しないIDを作らない |
| nod | `issue show --json`の回答原文、質問ID、askedBy、answeredBy、answeredAtを取得し、これらを出典として記録する。回答済みの質問へanswerを重ねない |

PM起点でaskedByがLLMの質問への一意なチャット実回答は、PM自身のactorのまま記録する。
人の発言を記録したことが分かるrationaleを先に残し、質問IDを明示してその質問だけを回答済みにする。
一括answerで関係ない質問を解消しない。
記録に失敗した場合は元workerへ回答せず、再取得して重複や部分成功を照合する。

```sh
nod -w <Workspace> issue log <IssueID> "<質問ID、実回答原文、出典、対応する選択肢、PMによる転記であること>" --kind rationale
nod -w <Workspace> answer <IssueID> "<利用者の実回答原文>" --question <質問ID> --json
nod -w <Workspace> issue show <IssueID> --json
```

人起点質問は上のanswerを実行しない。
チャット実回答の原文と出典はPMのlogへ保存し、`nod answer <IssueID> <回答原文> --question <質問ID>`を人自身が実行するよう案内する。
人がnodで回答するまで、その質問と該当作業の停止を保つ。

## 同じ作業への回答と再開

記録した実回答または既決事項の根拠を、質問を出した元messageへ渡す。
渡す内容はIssueと質問ID、回答原文と出典、決定した動作、維持する制約と`モデル:effort`である。
元のRun、Task、active Dispatch、terminalとworktree、実効設定の対応を照合し直し、不明なら追加起動せず停止する。
blocking askでは次の操作を使い、enqueueの成功後もworkerの状態や後続報告を確認する。

```sh
ORCA orchestration reply --id <元の質問messageID> --body "<記録した根拠または実回答と再開条件>" --json
```

質問がnodだけで、Orca blocking askがない場合は、現行ガイドの`send --to dispatch:<元DispatchID>`で同じ元作業へ伝える。
settle済みTaskを再開する必要がある場合は現行の所有権契約に従い、同じ実装者と実効設定で後続Taskを渡す。
実回答だけで他の未回答質問、未完了依存、仕様未合意、モデル不一致まで解除しない。
仕様準備の回答なら[仕様準備の手順](specification.md)へ戻り、正式Spec確認前に実装を再開しない。

回答の記録、replyのreceipt、再開先と残る停止条件をnodへ残す。
質問受付のみで人待ちになったDeliveryも、全行の対応と元message ID、待機条件をnodへ保存してからackする。
worker_doneを含む場合は、先に次の所有者または後片付けを決める既存手順を守る。
通信断や応答喪失時は再取得し、同じreplyや質問を無条件に再送しない。

人待ちの間も、既存workerがいる限りcheckを続ける。
独立したIssueは空き枠と候補条件の範囲で進め、回答待ちIssueとその依存先だけを止める。
