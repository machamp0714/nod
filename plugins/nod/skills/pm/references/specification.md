# needs-specの仕様準備

この手順は、候補表示を超えてIssueの進行を任されている場合に使う。
needs-spec付きIssueを通常の実装workerへ先に渡さず、既存の`nod:to-spec`へ接続する。
PMが独自の仕様作成手順や承認用DBを追加しない。

## 既存記録から仕様化を進める

最新のIssue本文、添付Document、Activity、質問、担当、依存、管理外実行を読み、他の停止理由や作業の所有者があれば保護する。
現在の`nod:to-spec`を読み、そのIssueの既存決定ログと途中経過から継続する。
別モデルの独立回答、未決論点の回答、仕様全体とテスト境界の合意を、それぞれ根拠付きで照合する。
別モデルの設定はユーザー指定と合意済み方針を尊重し、実際の報告と照合できない比較を実施済みと書かない。
既存の正式Specがある場合はto-specの規定どおり作り直すか追記するかを確認するが、既に合意された継続方針を聞き直さない。

本文の要求と完了条件は前提とし、変更提案と未決事項を分ける。
既に回答された論点、合意済み仕様、合意済みテスト境界は出典を確認して再利用し、文書が短いだけで承認を増やさない。
新たな利用者判断やモデル間で割れた未決論点は、[質問の手順](questions.md)の番号選択肢、推奨、理由、決定後の動作を添えて人へ戻す。
実回答の原文と出典を決定ログへ追記し、対象の仕様化の元工程へ戻す。
技術的に既決の質問と、利用者が新しく決める質問を混ぜない。
実装後のレビューが既存Specの受入条件を超える設計改善を求めている場合も、任意改善と要求変更を分ける。
PMが指摘対応のためにSpecを書き換えて必須化せず、新しい利用者判断なら上の質問手順へ戻す。
仕様全体とテスト境界の合意が足りなければ、その不足を解消するまで正式Spec完成や実装可能と扱わない。

## 仕様化中の既存workerの監督

仕様化を始める前、別モデル照合を待つ間と結果取得後、人への質問を出した直後、Spec作成や添付へ進む前に、Orcaのcheckで既存workerの通知を処理する。
照合が長くかかる場合は非同期の既存手順を使い、仕様化の同期処理で監督を止めない。
人の回答待ちでも既存workerの質問、問題、完了報告を処理し、Deliveryの全行を確認する。
未決の仕様Issueだけを停止し、その待機を理由に独立したworkerの根拠付き回答を止めない。
worker質問には[質問の手順](questions.md)で回答し、元Dispatchとmessageの対応を記録する。
worker_doneがあれば既存の実装報告と所有権処理へ渡し、仕様化が終わるまで通知を放置しない。

## 正式Specの添付とラベル解除

needs-spec解除は`nod:to-spec`の正式な仕様作成と添付確認の工程だけで行う。
PMが着手条件を作る目的で先にラベルを外さない。
to-specの作成または合意済み追記が完了した後、次を実CLIで確認する。

```sh
nod -w <Workspace> doc show <正式SpecのDocumentID> --json
nod -w <Workspace> issue show <IssueID> --json
```

Documentのkindがspecで、対象Issueへのリンクがあり、本文を読めることを確認する。
別IssueのSpec、kind=docの決定ログ、添付前の草稿、workerの「仕様化済み」という報告だけで代用しない。
未決論点の実回答、仕様とテスト境界の合意が決定ログで確認でき、その決定がSpec本文に反映されていることも確認する。
これらの確認後だけ、to-specの最終工程でneeds-spec解除、ready-for-agent付与、決定要約の記録を行う。
解除や添付に失敗すればSpecを保持して停止し、失敗を記録する。

解除後もIssueを再取得し、Specの添付、needs-specがないこと、未回答質問、依存、担当、仕様判定、既存実行と空き枠を再確認する。
条件が揃えば、もともと任された進行範囲に従って同じIssueを[実装手順](implementation.md)へ渡す。
PMに既に実装から提出まで任されている場合は、to-specの完了案内を追加の計画化や再承認の必須条件にしない。
候補表示や仕様準備までの依頼なら、その範囲の成果と残る条件を報告して止める。
