# nod:code-review

`HEAD` と、ユーザーが指定した基点との差分を 2 軸でレビューする。

- **Standards**: このリポジトリの文書化された規約に沿っているか
- **Spec**: 元の Issue / 仕様を忠実に実装しているか

2 軸は互いの文脈を汚さないよう **並列のサブエージェント** で行い、このスキルが結果を並べる。

## 1. 基点を決める

ユーザーが言ったもの（コミット SHA、ブランチ名、タグ、`main`、`HEAD~5` など）が基点。無ければ聞く（`nod:implement` から呼ばれたときは、デフォルトブランチとの merge-base を使う）。

差分のコマンドを 1 度だけ決める: `git diff <基点>...HEAD`（3 点。merge-base と比べる）。コミット一覧は `git log <基点>..HEAD --oneline`。

先に `git rev-parse <基点>` が解決できることと、差分が空でないことを確かめる。参照の誤りや空の差分は、サブエージェントを起動する前にここで止める。未コミットの変更は対象外なので、必要ならコミットしてから実行するよう伝える。

## 2. 仕様を探す

次の順で探す。

1. 引数で渡された Issue id か Document のパス
2. 今のブランチを作業場所として記録している nod の Issue（`nod issue list --json` の `branch` が今のブランチと一致するもの）。ブランチ名・コミット・PR には nod の Issue ID を書かない決まりなので、そこから ID を読み取らない。`nod issue show <id>` の Documents から kind=spec の Document を取り、`nod doc show <Document id>` で全文を読む。計画（Task と Step）も受け入れ条件として使う
3. 見つからなければ、仕様の場所をユーザーに聞く。無いと言われたら、Spec のサブエージェントは飛ばし「仕様なし」と報告する

## 3. 規約を集める

`CODING_STANDARDS.md`・`CONTRIBUTING.md`・`CLAUDE.md`・`AGENTS.md` など、コードの書き方を文書化したもの。

それに加えて、Standards の軸には常に下の **臭いの基準**（Fowler『リファクタリング』3 章のコードの臭い）を載せる。リポジトリが何も文書化していなくても使う。

- **リポジトリが優先。** 文書化された規約が常に勝つ。規約が認めているものは、基準が指摘しても抑える。
- **常に判断の余地がある指摘。** 臭いは「〜の可能性」というラベル付きの目安で、違反とは書かない。ツールが強制している内容は扱わない。

各臭いは「何か → どう直すか」。差分に当てはめる。

- **Mysterious Name**: 何をする・何を持つかが名前から読めない関数・変数・型 → 名前を変える。正直な名前が浮かばないなら設計が濁っている
- **Duplicated Code**: 同じ形のロジックが変更内の複数箇所にある → 共通の形を抜き出して両方から呼ぶ
- **Feature Envy**: 自分のデータより他のオブジェクトのデータに手を伸ばすメソッド → そのデータの側へ移す
- **Data Clumps**: 同じいくつかの値や引数がいつも一緒に動く（生まれたがっている型） → 1 つの型にまとめて渡す
- **Primitive Obsession**: 独自の型に値するドメインの概念を、プリミティブや文字列で表している → 小さな型を与える
- **Repeated Switches**: 同じ型への `switch` / `if` の連鎖が変更内で繰り返される → ポリモーフィズムか、両方が使う 1 つの対応表にする
- **Shotgun Surgery**: 1 つの論理的な変更のために、差分の多くのファイルに散らばった修正が要る → 一緒に変わるものを 1 つのモジュールに集める
- **Divergent Change**: 1 つのファイル・モジュールが、関係のない複数の理由で変更されている → 変わる理由ごとに分ける
- **Speculative Generality**: 仕様に無い要求のための抽象・引数・フック → 消す。本当に要るまでインライン化する
- **Message Chains**: 呼び出し側が依存すべきでない `a.b().c().d()` の長いたどり → 最初のオブジェクトの 1 メソッドの後ろに隠す
- **Middle Man**: ほとんど委譲しているだけのクラス・関数 → 外して本来の相手を直接呼ぶ
- **Refused Bequest**: 継承したものの大半を無視・上書きするサブクラスや実装 → 継承をやめて委譲にする

## 4. 2 つのサブエージェントを並列に起動する

両方のプロンプトの最後に、必ず次の一文を入れる。

> `code-review`（`nod:code-review` を含む）を呼ばず、エージェントも増やさず、このレビューを自分で直接行うこと。

**Standards のサブエージェント** に渡すもの:

- 差分のコマンドとコミット一覧
- 3 で見つけた規約ファイルの一覧と、**臭いの基準の全文**（サブエージェントは他の手段でこれを読めない）
- 指示: 「ファイル・hunk ごとに、(a) 文書化された規約に反する箇所（根拠のファイルと規則を引く）、(b) 見つけた臭い（名前と hunk を引用）を報告する。規約違反は確定の違反になりうるが、臭いは常に判断の余地がある指摘として区別する。規約は基準より優先する。ツールが強制している内容は扱わない。400 語以内」

**Spec のサブエージェント** に渡すもの:

- 差分のコマンドとコミット一覧
- 仕様の全文（と、あれば計画の Task・Step）
- 指示: 「(a) 仕様が求めたのに欠けている・不完全な要求、(b) 差分にあって求められていない振る舞い（スコープの膨張）、(c) 実装されているように見えて誤っている要求を報告する。各指摘に仕様の該当行を引用する。400 語以内」

仕様が無ければ Spec のサブエージェントは飛ばし、最終報告にそう書く。

## 5. まとめる

2 つの報告を `## Standards` と `## Spec` の見出しの下に、そのまま（または軽く整えて）並べる。指摘を混ぜたり、軸をまたいで順位を付け直したりしない。

最後に 1 行で、軸ごとの指摘数と、軸ごとの最も重い指摘（あれば）を書く。軸をまたいで 1 つの勝者を選ばない（2 軸を分けている意味がなくなる）。

サブエージェントの指摘は仮説であり、各指摘の引用元を確かめてから扱うよう、報告に添える。

## なぜ 2 軸か

変更は片方の軸だけを満たすことがある。

- 規約はすべて守っているが、違うものを実装している → Standards は合格、Spec は不合格
- Issue の求めどおりだが、規約を破っている → Spec は合格、Standards は不合格

別々に報告すれば、一方がもう一方を覆い隠さない。

## 完了時のネクストアクション

単独で呼ばれたときは、次の一手を番号付きで示し、おすすめを 1 つ理由つきで添えて、ユーザーの選択を待つ（自分から次へ進まない）。`nod:implement` から呼ばれたときは示さず、結果を返すだけにする。

1. 指摘に対応する
2. 対応せずに進める（PR を作るなど）
