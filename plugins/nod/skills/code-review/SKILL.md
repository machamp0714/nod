# nod:code-review

`nod review` で対象と要求を固定し、実装者と異なるモデルによるStandards・Specの独立確認を報告する。
このSkillをClaude Code・Codexのどちらから呼んでも、レビュー担当のprovider・モデルは別に指定する。

## 1. 対象と実行モードを決める

- 対象リポジトリと基点を利用者の指定から決める。基点がなければ確認する。`nod:implement` からの呼び出しでは、対象repoのデフォルトブランチとのmerge-baseを基点にする。
- 従来の `nod:code-review <基点>` は基点のmerge-baseからHEADまでのコミット差分を読む。PRの指定でも実際のrepo・基点・対象HEADを特定する。GitHub参照は `gh` を使う。
- 未コミット変更は明示された場合だけ `--local` で含める。指定された未追跡ファイルだけ `--untracked <相対パス>` へ渡す。通常のレビューのためにcommitやstashを作らない。
- 自動修正は明示された場合だけ有効にし、そのときだけ [隔離修正とpatch受け渡し](references/repair.md) を読む。指定がなければレビューだけを行う。
- `nod review run --help` で入口が存在することを確認する。未対応CLIなら更新が必要と報告し、旧手順へ黙って代替しない。インストールや設定変更はこのSkillから自動で行わない。

## 2. 要求と規約を確認する

[入力・モデル設定・実行](references/execution.md) の準備コマンドを使う。
明示Issueまたは要求Documentを優先し、未指定ならCLIにbranchと作業場所から解決させる。ブランチ名からIssue IDを推測しない。

`preparation.json` の `sources` と `requirements` を読み、Issueの確定要求、kind=spec全文、現在計画のTask・Step、適用規約が含まれることを確認する。
Specが存在しない場合だけIssue本文を使う。取得失敗・矛盾・正本不明を無視してSpec軸を省略しない。
READMEや配下の規約など、対象repoで実際に適用される資料と `sources` の一覧を照合する。CLIが固定していない必須規約があればレビューを始めず、未完了と不足資料を報告する。CLIは変更ファイルの祖先にあるREADMEを含む規約と参照先を固定するが、それ以外の独自資料に適用規約がないかも確認する。

固定sourcesの規約を読み、今回の差分に適用する必須範囲と参考範囲を根拠付きで分ける。構成の説明や一般的な改善指針を、リポジトリ全体の監査要求に変えない。[入力・モデル設定・実行](references/execution.md)の規約適用計画を作り、`--scope-plan` で渡す。リンク先を一律に必須要求と扱わず、件数を減らすために必須規約を除外しない。適用不明は未確認とし、Issue・Spec・承認計画はこの仕組みで除外しない。

Spec全文の各確認単位を残し、要求と説明を区別する。背景・根拠・範囲・未検証領域の説明だけなら、実装の充足とは別に確認記録を残す。必須要求が混ざる文や分類が不明な文を説明扱いで除外しない。判定形式は[本文分類と指摘の対応](references/execution.md#本文分類と指摘の対応)を参照する。

実行前に、要求の確認対象がコード・指示文の内容、機械的な検査の合否、実動作の評価のどれかを、原文の主語・条件・今回の成果物から確認する。[確認対象と担当の準備](references/execution.md#確認対象と担当の準備)に従い、機械的な合否だけの要求は `--responsibility-plan` で事前に自動チェック担当へ分ける。指示文に書かれた操作を親が実行せず、実動作評価の未実施を静的な指示違反と混同しない。複合行の意味・設計の要求を丸ごと除外しない。

`prepared` は入力準備の完了であり、レビュー合格ではない。空差分・不正な基点・必要資料の取得失敗なら、モデルを起動せず理由を返す。

## 3. 異なるモデルでレビューする

[入力・モデル設定・実行](references/execution.md) に従い、利用者の具体的な設定と実装した実効モデルID集合を使って `nod review run` を1回起動する。
既に確認できる設定や許可を尋ね直さない。不明な実装モデルや追加使用設定を推測で埋めない。

CLIがStandards探索とSpec探索を並列実行し、その後に別コンテキストの候補検証を起動する。工程はこの3つのまま、各工程はCLI内部で確認単位を最大80単位ずつに分割し、モデルCLIを同時最大8プロセスで実行して工程ごとに集約する。このSkill側でレビュアーを増やしたり分割を起動したりせず、子からSkillやエージェントを再帰起動しない。
実装者の自己評価や探索の思考過程を検証へ渡さない。固定コード・要求・候補と読解による証拠を用いる。Biome・lint・型検査・テスト・再現コードを実行せず、結果や診断も受け取らない。自動チェックとレビューは独立したレイヤである。

base（merge-base）との差分を起点に、今回発生・悪化した具体的な不具合と、今回の明示要件の実装漏れだけを確認する。関連コードは変更の影響・契約・防御を調べるために読み、変更行だけに限定しない。指摘数のノルマや全体の改善点探しは行わない。
候補にも担当と根拠を記録する。自動チェック担当の候補が混入した場合は監査用に対象外として残し、未確認の停止理由にしない。hookやCIの設計不備まで除外しない。
整理・重複・表記・好み・将来の仮定だけの改善案は、差分内でも候補にしない。要対応は到達条件・契約違反・具体的影響・証拠を必要とする。任意の設計案の選択を必須仕様の未決と扱わない。原因統合だけを理由に採否をそろえない。

## 4. 結果と対象版を確認する

最上位の `status`、`score`、`target`、両軸の `review`、`coverage`、`findings`、`problems`、`remaining` を読む。
モデル工程の終了コード0や `execution.status=completed` だけで合格としない。
準備コマンドから実行までに対象や要求が変わった場合は、実行結果の固定版を明示し、依頼された版との一致を確認する。

- `completed` かつ5点は、表示された対象・確認範囲で両軸の必要確認が終わり要対応0件であることを表す。
- 0〜4点は確認済み要対応の最重影響を表す。任意提案を減点したり、軸間の平均で相殺したりしない。
- `incomplete` は最終点数なし（`null`）。確認済み指摘・未確認・停止理由・保存済み成果を残す。過去の5点を最終点数へ転用しない。
- `coverage` の要求ごとの充足・未充足・未確認・対象外・説明確認（`context`）と分類根拠・実装・検証証拠を省略しない。限定範囲の合格をIssue全体の充足と説明しない。
- `origin: pre_existing` は基点から存在する課題。今回悪化せず修正も要求されていない課題は、変更の影響確認中に見つかった場合だけ基点・範囲の根拠付きで対象外として別枠報告し、採点・未完了判定・自動修正から除く。今回の明示要件は対象内、範囲不明は未確認とする（判定形式はexecution.md）。
- `initialReviewPath` の初回結果を修正後の結果で上書きしない。修正時は最終対象とpatchの対応も確認する。

失敗したときだけ [停止理由と再開](references/recovery.md) を読み、必要な不足情報や再開条件を示す。
同じ失敗を無条件に繰り返さず、再実行には新しい実行IDを使う。

## 5. 根拠付きで報告する

[報告雛形](assets/report.md) を読み、対象・実行状態・点数・Standards・Spec・要求対応・未確認・保存先を実際の結果で埋める。
要対応と必要な未確認を報告し、偶然見つかった対象外は根拠付きで別枠にする。混入したoptionalはJSON・保存記録の監査情報として保持し、通常の報告では提案しない。同一原因は共通IDで関連付けるが軸別の出典・採否を消さない。
要求対応が長い場合は全文の報告ファイルを保存してリンクし、チャットの要約だけで要求別記録を置き換えない。

自動チェックの成否をレビューの点数へ混ぜない。5点は無欠陥の保証や自動マージ許可ではない。対象repoの既存マージ条件を維持する。
local対象や隔離修正後の結果を、元HEAD・後で作成したcommitへの承認に転用しない。現在commitへのレビューが必要ならそのcommitを対象に確認する。

`nod:implement` から呼ばれた場合は結果を返して終了する。単独レビューも報告で終了し、明示された修正範囲を超えて修正・commit・push・PR投稿・マージを行わない。次の判断が必要な場合だけ、具体的な選択肢を番号付きで示し、おすすめと理由を添える。
