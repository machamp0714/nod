# 反証の手順

この手順は、定義 `code-reviewer-refute` で起動され、依頼本文が `役割: 反証` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、観点と判断基準、候補の必須項目、判定の語彙）に従う。点数は計算しない（親の役割）。

## 1. 入力を確かめる

- 読むのは、依頼本文に列挙された `refute-input/` のファイル、`target.md` の対象リポジトリ（担当用の限定 clone）、依頼本文が示す依存の写しだけ。作業ディレクトリの他の場所（探索担当のサブディレクトリ・`notes/`・親専用領域）、探索担当の返答・履歴は読まない。
- 依頼本文の入力ファイルの一覧・書いてよい場所・出力のパスが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- `manifest.md` の sha256 と、受け取った `target.md`・`requirements/`・`local/`・`deps-files.sha256` を照合し、不一致は不足として記録する。
- 引き渡し用ファイルは、探索担当の候補と、Spec 探索の要求資料ごとのコード要求・コード要求の対応表として読む。候補の証拠や対応表の状態を正しいと前提にせず、固定版から確かめ直す。

## 2. 候補を判定する

- 両方の引き渡し用ファイルのすべての候補を、要対応／棄却／未確認／基点から存在（対象外）／任意のどれかに判定し、根拠を書く。候補を黙って落とさない。
- 到達条件・期待動作・破綻・影響・証拠を、固定版のコードと契約・要求の原文で確かめる。差分（`git -C <repo> diff --no-ext-diff --no-textconv <merge-base> <head>`、`mode: local` では写しを重ねたもの）と関連コードを読み、必要なら規約の適用も原文から判断し直す。
- 軸は破った契約で確かめ直す。明示された要求と既存の契約の両方を破る場合は、期待動作の出典にした契約で軸を決め、もう一方を関連として示す。
- 要対応に影響度 0〜4 を付ける（SKILL.md の定義）。到達条件が限定的という理由だけで下げない。
- 両探索が同じ原因を挙げた候補は `CAUSE-<n>` でまとめ、重複件数として数えない。各候補の ID・発見者の区分・判定は残す。まとめることを理由に採否をそろえない。採否一覧の同一原因の欄に同じ `CAUSE-<n>` を書き、要対応の節の `CAUSE-<n>` の影響度は、含まれる要対応の候補の影響度のうち最も重いもの（最小値）にする。
- 基点から存在する候補は、merge-base に同じ内容があることと、今回悪化・顕在化させていないこと、今回の明示要求が修正を求めていないことを確かめたときだけ「基点から存在（対象外）」にする。今回の明示要求が修正を求めるものは対象外にしない。

## 3. 見落としを探して追加する

- 探索の候補に無い不具合を、正しさ・セキュリティ・性能・並行性の4観点で自分で探す。出発点は両軸のもの（規約・既存の公開契約・防御・状態管理・差分の波及と、要求ごとの実装・境界条件・異常系・要求された性能・権限・同時操作）を使い、探索が触れていない変更箇所・関連コード・要求を優先する。探索担当の参照ファイルは読まない。
- 見つけた不具合は `REF-<n>` とし、必須項目に加えて発見者の区分「反証で追加」と起点（今回の差分／基点から存在）を書く。判定と影響度も付ける。要対応なら採点に入る。
- 見つからなければ、採否一覧の節に「反証で追加した発見なし」と明示する。

## 4. コード要求の対応表を確定する

- `requirements/` の要求資料を原文から読み直し、Spec 探索の対応表に無いコード要求（SKILL.md 3節）を見つけたら行を足す。足した行は、証拠または不足理由の欄の先頭に「（追加）」とだけ書く。
- Spec 探索の対応表の各行を、確定した対応表に残すか、コード要求でないとして「表から除いた行」の節へ移す。移す行は、Spec 探索の対応表と同じ要求の出典と1行の理由だけを書く（分類名や件数は書かない）。行を除いても、その行の候補の採否は採否一覧に残す。実行・ブラウザ・実環境で確かめる要求であることや「本番・承認・デザイン・画面」などの語を含むことだけを理由に、コードで読める部分のある行を除かない。
- 要求資料ごとのコード要求あり／なしを、確定した対応表に合わせて書き直す。コード要求が0件なら、行の無い対応表を正常な結果とする。
- コード要求全体の充足の証拠を確かめた行だけを「充足」にする。対応する要対応があれば「未充足」、コードレベルで結論を出せなければ「未確認」とする。状態は 充足／未充足／未確認 だけを使う。
- 「未確認」にしてよいのは SKILL.md 5節の4つ（コード要求の中身を決める要求資料の不足、結論に必要な依存の契約の不足、要求間の矛盾、採否を確定できない候補）だけで、理由と確かめる担当と、どのコード上の結論にどの契約・資料が足りないかを書く。依存の写しが無いことや、参照する Document があることだけでは未確認にしない。ブラウザ・実環境・作業手順の確認を未確認の理由にしない。
- 候補の棄却だけで「充足」へ変えない。
- 基点から存在する課題でも、今回の明示要求が修正を求めるなら「基点から存在（対象外）」にしない。
- 要求間の矛盾（置き換え関係が不明な複数の `kind=spec` など）は、該当する行を未確認にし、未確認の節に種別「要求間の矛盾」と確かめる担当を書く。
- 未確認が残っても、判定と対応表を確定して返す。未確認を理由に、他の候補の採否や確定した要対応を保留しない。

## 5. 書く

- 作業中の考え・検討の過程は `refute/notes/` に書く。
- 判定本文 `refute/verdict.md` は [反証の判定本文の雛形](../assets/refute-verdict.md) に従って書き、改行で終える。親はこの本文を書き換えずに報告へ収録する。
- 軸ごとの結果には、軸ごとに要対応と未確認の件数を書く（0件でも書く）。要対応の件数は要対応の節のその軸の見出しの数（同一原因は1件）、未確認の件数は未確認と理由の表のその軸の行数と同じにする。軸を「未完了」とは書かない（最終状態は、必要な担当の有効な結果の有無で親が決める）。
- 未確認と理由の節は、自由記述ではなく雛形の表にする。判定が未確認のすべての候補（種別「候補」）と、状態が未確認の対応表のすべての行（種別「要求」、矛盾なら「要求間の矛盾」）を1件1行で、要求の出典（または候補 ID）・軸・種別・理由・確かめる担当・不足箇所を書く。確かめる担当に廃止した担当（受け入れ確認担当・自動チェック担当）を、理由に「要実行確認」を書かない。
- 判定本文の節・表・欄は、親のスクリプトが機械的に読み、読み取れない・食い違う（採否一覧の漏れ、要対応の影響度の欠落、同一候補の判定の不一致、Spec 探索の行が確定した対応表にも表から除いた行にも無い、要求資料ごとのコード要求の欠落、未充足の行に要対応が無い、未確認の行が未確認と理由の表に無い、軸ごとの件数と個別の判定の不一致、廃止した状態・分類・担当・理由の使用など）ときは、判定の中身にかかわらず無効な結果になる。雛形の見出し・列・語彙を変えない。スクリプトの検査は形式と整合だけで、コード要求の取り落としが無いことは保証しない。
- 任意と判定した候補は監査用の採否一覧にだけ載せ、要対応の節で提案しない。
- 親への返答は、出力のパスと終了状態だけにする。
