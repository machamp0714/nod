# 反証の手順

この手順は、定義 `code-reviewer-refute` で起動され、依頼本文が `役割: 反証` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、観点と判断基準、候補の必須項目、判定の語彙）に従う。点数は計算しない（親の役割）。

## 1. 入力を確かめる

- 読むのは、依頼本文に列挙された `refute-input/` のファイル、`target.md` の対象リポジトリ（担当用の限定 clone）、依頼本文が示す依存の写しだけ。作業ディレクトリの他の場所（探索担当のサブディレクトリ・`notes/`・親専用領域）、探索担当の返答・履歴は読まない。
- 依頼本文の入力ファイルの一覧・書いてよい場所・出力のパスが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- `manifest.md` の sha256 と、受け取った `target.md`・`requirements/`・`local/`・`deps-files.sha256` を照合し、不一致は不足として記録する。
- 引き渡し用ファイルは、探索担当の候補と要求ごとの対応表として読む。候補の証拠や対応表の状態を正しいと前提にせず、固定版から確かめ直す。

## 2. 候補を判定する

- 両方の引き渡し用ファイルのすべての候補を、要対応／棄却／未確認／基点から存在（対象外）／任意のどれかに判定し、根拠を書く。候補を黙って落とさない。
- 到達条件・期待動作・破綻・影響・証拠を、固定版のコードと契約・要求の原文で確かめる。差分（`git -C <repo> diff --no-ext-diff --no-textconv <merge-base> <head>`、`mode: local` では写しを重ねたもの）と関連コードを読み、必要なら規約の適用も原文から判断し直す。
- 軸は破った契約で確かめ直す。明示された要求と既存の契約の両方を破る場合は、期待動作の出典にした契約で軸を決め、もう一方を関連として示す。
- 要対応に影響度 0〜4 を付ける（SKILL.md の定義）。到達条件が限定的という理由だけで下げない。
- 両探索が同じ原因を挙げた候補は `CAUSE-<n>` でまとめ、重複件数として数えない。各候補の ID・発見者の区分・判定は残す。まとめることを理由に採否をそろえない。
- 基点から存在する候補は、merge-base に同じ内容があることと、今回悪化・顕在化させていないこと、今回の明示要求が修正を求めていないことを確かめたときだけ「基点から存在（対象外）」にする。今回の明示要求が修正を求めるものは対象外にしない。

## 3. 見落としを探して追加する

- 探索の候補に無い不具合を、正しさ・セキュリティ・性能・並行性の4観点で自分で探す。出発点は両軸のもの（規約・既存の公開契約・防御・状態管理・差分の波及と、要求ごとの実装・境界条件・異常系・要求された性能・権限・同時操作）を使い、探索が触れていない変更箇所・関連コード・要求を優先する。探索担当の参照ファイルは読まない。
- 見つけた不具合は `REF-<n>` とし、必須項目に加えて発見者の区分「反証で追加」と起点（今回の差分／基点から存在）を書く。判定と影響度も付ける。要対応なら採点に入る。
- 見つからなければ「反証で追加した発見なし」と明示する。

## 4. 要求ごとの対応表を確定する

- Spec 探索の対応表のすべての行を確定する。要求の写しに対応表で覆われていない確認単位があれば行を足し、足したことを書く。
- 要求全体の充足の証拠を確かめた行だけを「充足」にする。対応する要対応があれば「未充足」、証拠が足りなければ「未確認」とする。「未確認」の行には、理由と確かめる担当を書く（実行しないと分からない挙動は、再現も実行もせずに理由「要実行確認」・担当「人」とする）。
- 候補の棄却だけで「充足」へ変えない。「説明」「自動チェック担当」「受け入れ確認担当」「対象外」を充足へ丸めない。
- コードの静的な読みでは確かめられず、作業記録・成果物・配置の証拠または Git 外の外部の正本で確かめる要求（作業のしかた・配置・作業記録を求める要求、外部の正本との一致・更新順序を求める要求）の行だけを「受け入れ確認担当」にする（Spec 探索が「未確認」とし確かめる担当を受け入れ確認担当とした行も、原文から確かめ直して決める）。実行しないと分からない挙動は、既存の実行の記録があっても受け入れ確認担当にせず、要実行確認の未確認のままにする。
- 複合要求は、コードから判断できる部分の行と、受け入れ確認担当の行に分ける（同じ出典の後ろに、その行が扱う部分を短く書いて区別する）。コードから判断できる部分は充足・未充足・未確認などで判定し、その部分の要対応は採点に残す。要求全体を受け入れ確認担当にして、要対応や未確認を対応表と点数から落とさない。
- 「受け入れ確認担当」の各行について、判定本文の「受け入れ確認担当の行」の節に、確かめること（要求された成果物と、要求された作業・手順・配置を分けて）と、必要な外部の正本（出典と版。要らなければ「なし」）を書く。成果物や記録の有無は自分で確かめない（受け入れ確認担当の役割。反証担当は nod を読まない）。
- 受け入れ確認担当の行に対応する候補（その行の作業記録・成果物・配置・外部の正本の確認だけで採否が決まり、コードから判断できる不具合を含まない候補）は、判定を「未確認」、理由を「受け入れ確認担当の行で確かめる」、確かめる担当を「受け入れ確認担当」とし、その行の候補ID列に書く。親はこの候補を、その行の受け入れ確認の判定で扱う（別の確認が残る事項として重ねない）。コードから判断できる部分を含む候補は、その部分を他の候補と同じく判定する。
- 基点から存在する課題でも、今回の明示要求が修正を求めるなら「対象外」にしない。
- 要求間の矛盾（置き換え関係が不明な複数の `kind=spec` など）は、該当する行を未確認にし、未確認の節に「要求間の矛盾」と確かめる担当を書く。受け入れ確認担当の行は未確認の節に書かない（受け入れ確認の結果が返った後に、親が結果に応じて確認が残る事項にする）。
- 未確認が残っても、判定と対応表を確定して返す。未確認を理由に、他の候補の採否や確定した要対応を保留しない。

## 5. 書く

- 作業中の考え・検討の過程は `refute/notes/` に書く。
- 判定本文 `refute/verdict.md` は [反証の判定本文の雛形](../assets/refute-verdict.md) に従って書き、改行で終える。親はこの本文を書き換えずに報告へ収録する。
- 軸ごとの結果には、軸ごとに要対応と未確認の件数を書く（0件でも書く）。軸を「未完了」とは書かない（最終状態は、必要な担当の有効な結果の有無で親が決める）。
- 未確認と理由の節には、未確認の候補・要求ごとに、要求の出典（または候補 ID）・理由・確かめる担当・不足箇所を書く。
- 受け入れ確認担当の行の節には、対応表で「受け入れ確認担当」とした行を1行ずつ、対応表と同じ要求の出典で書く。その行が無ければ「なし」と書く（親はこの節と対応表から、受け入れ確認担当を起動するかを決める）。
- 任意と判定した候補は監査用の採否一覧にだけ載せ、要対応の節で提案しない。
- 親への返答は、出力のパスと終了状態だけにする。
