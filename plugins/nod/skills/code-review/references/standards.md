# Standards 探索の手順

この手順は、定義 `code-reviewer-standards` で起動され、依頼本文が `役割: Standards 探索` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、観点と判断基準、候補の必須項目、判定の語彙）に従う。採否・影響度・点数は決めない（反証担当と親の役割）。

## 1. 入力を確かめる

- 依頼本文の作業ディレクトリ・読んでよい入力・書いてよい場所・出力のパスを確かめる。どれかが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- `input/target.md` から対象リポジトリ（担当用の限定 clone）・mode・merge-base・head（`mode: local` では土台の HEAD と写し）・依存の写しの場所を読む。`input/manifest.md` の sha256 と `input/` の各ファイル（依存の写しの指紋の一覧 `deps-files.sha256` を含む）を照合し、不一致や取得できなかった資料は不足として記録する。
- `input/requirements/` の要求の原文を読む。規約の適用と、既存の契約が今回の要求で変わるかの判断に使う。

## 2. 差分と関連コードを固定版から集める

- 差分は `git -C <repo> diff --no-ext-diff --no-textconv <merge-base> <head>`（必要に応じて `--stat`・`--name-status`・`-M`）で読む。
- `mode: local` では、さらに `local/changes.diff` と `local/untracked/` を土台の HEAD に重ねて読む。重ねた内容を読む必要があれば、自分の一時ディレクトリに `git -C <repo> archive <土台の HEAD> | tar -x -C <一時ディレクトリ>` で展開し、その中で `git apply <changes.diff>` を当て、未追跡の写しを置く。
- 変更ファイルだけでなく、呼出元・呼出先・状態の保存先・防御・公開契約・テストを固定版で読む。基点から存在するかは merge-base の版（`git -C <repo> show <merge-base>:<path>`）で確かめる。
- 依存の版は固定版の lockfile で、依存のコードは依存の写しで確かめる（SKILL.md の3節）。写しに無いものは外部へ取りに行かず未確認とする。

## 3. 規約を集め、適用を判断する

- リポジトリ内の規約を head の版から集める。少なくとも、変更ファイルの祖先ディレクトリにある `AGENTS.md`・`CLAUDE.md`・`CODING_STANDARDS.md`・`CONTRIBUTING.md`・`README.md` と、そこからリンクされたリポジトリ内の資料を見る。それ以外にも必須の規約を定める資料（設定ファイル・ドキュメント）があれば含める。
- Git 管理外の Workspace の規約は `input/requirements/workspace-rules.md` から読む。
- 差分が規約そのものを変えている場合は、基点の版との違いと、どちらの版を適用したかを記録する。
- 各規約について、今回の差分への適用を「必須／参考／未確認」で判断し、理由を書く。リンク先を一律に必須にせず、規約が必読とする資料は辿る。件数を減らすために必須の規約を外さない。適用を判断できなければ未確認とし、理由を書く。

## 4. 不具合を探す

正しさ・セキュリティ・性能・並行性の4観点すべてで探す。主な出発点は次のとおり。

- 適用した規約: 差分が必須の規約に反していないか。
- 既存の公開契約: CLI・API・データ形式・設定・ドキュメントで約束した振る舞いを、差分が壊していないか。
- 防御: 入力検証・権限・エラー処理・境界の防御を、差分が外したり迂回させたりしていないか。
- 状態管理: 保存・移行・キャッシュ・トランザクション・後片付けの整合を、差分が崩していないか。
- 差分の波及: 変更した関数・型・定義の利用側で、到達条件が変わって壊れる箇所がないか。

性能は実在する入力規模・処理の増幅・要求との関係を、並行性は到達可能な実行順序と破綻を固定版の証拠で示す。見つけた不具合が明示された要求を破るなら、軸は Spec とし、候補 ID は `STD-<n>` のまま書く。

## 5. 書く

- 作業中の考え・読んだ箇所の控え・検討の過程は `standards/notes/` に書く。
- 引き渡し用ファイル `standards/handoff.md` は [Standards 探索の雛形](../assets/standards-handoff.md) に従って書く。暫定の重大度・確信度・要約・推論・総合判断・原因の統合を書かない。
- 候補が無ければ「候補0件」と明示する。必須の資料が足りず確かめられなかった点は、部分レビューへ縮小せず、未確認として理由と不足箇所を書く。
- 書き終えたら、禁止項目が無いこと、各候補の必須項目がそろっていることを自分で見直す。
- 親への返答は、出力のパス・終了状態（完了／未確認を含む）・候補の件数だけにする。候補の内容や見立ては返答に書かない。
