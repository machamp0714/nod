# 受け入れ確認の手順

この手順は、定義 `code-reviewer-acceptance` で起動され、依頼本文が `役割: 受け入れ確認` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、判定の語彙）に従う。コードの不具合の探索、候補の判定、対応表の状態の変更、点数の計算はしない（探索・反証・親の役割）。

## 1. 入力を確かめる

- 読むのは、依頼本文に列挙された `acceptance-input/` のファイル、`target.md` の対象リポジトリ（担当用の限定 clone）、依頼本文が示す依存の写しだけ。作業ディレクトリの他の場所（探索・反証のサブディレクトリ・`notes/`・親専用領域とそこにある親のテスト実行の記録）、他の担当の返答・履歴、nod は読まない。Activity・添付 Document・参照された記録・外部の正本は、親の写しだけを読み、写しの出典のパス・URL・Git のリポジトリを開きに行かない。
- 依頼本文の入力ファイルの一覧・書いてよい場所・出力のパスが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- `manifest.md` の sha256 と、受け取った `target.md`・`requirements/`・`local/`・`deps-files.sha256` を照合する。`records.md` の sha256 と、`refute-verdict.md`・`records/`・`evidence/` の各ファイルを照合する。不一致は不足として記録する。
- `records.md` の項目 ID・取得時刻・出典・版・読み取りの方法・識別情報・取得不能と理由を読む。取得不能とされた証拠は、自分で取りに行かない（外部の正本や配置先の元の場所、URL も開かない）。
- `refute-verdict.md` は、確かめる行（対応表で状態が「受け入れ確認担当」の行と、「受け入れ確認担当の行」の節）を知るために読む。反証の判定・結論・証拠を、受け入れ確認の証拠にしない。

## 2. 担当行を確かめる

- 対象は、`refute-verdict.md` の要求ごとの対応表で状態が「受け入れ確認担当」の行すべてとする。それ以外の行は判定しない。担当行を黙って落とさない。要求の範囲は `requirements/` の原文で確かめ、読み足さない。
- 行ごとに、要求が求める部分を次の5つに分けて確かめる。要求が求めていない部分は「対象外（要求が求めていない）」と書く。
  - 成果物の不変版の存在: 要求された成果物の、版を特定できる不変の写し（対象版の commit の中身、版を名前に持つ配置物、指紋付きの実行記録など）があること。
  - 作業・手順の実施: 要求された作業・手順（実行・記録・配置の操作など）を行ったこと。
  - 現在の配置: 要求された版が、配置先に今置かれていること。配置先の観測（`observation.txt` の出典のパス・バイト数・sha256）と写したファイルの内容を、対象版と対応させて確かめる。成果物の不変版があることだけでは、現在の配置を確かめたことにしない。配置先がリンク・ディレクトリなどで取得不能とされたときは「確かめられず」とする。
  - 外部の正本との内容の一致: 名指しされた外部の正本の写しの内容と、対象版（または要求が示す成果物）の内容が一致すること。
  - 更新順序: 要求が求める順序（例: デザインの更新の後に実装した）。版履歴（commit の時刻と順序、版の記録など）の証拠で確かめる。取得時刻・指紋・ファイルの更新時刻・自己申告だけでは順序を確かめたことにしない。
- 証拠にしてよいのは、`acceptance-input/` の写し（Activity・添付 Document・参照された記録・外部の正本とその観測）と、限定 clone の固定版（commit・ファイル・履歴）と依存の写しだけ。どの写しのどこ（`records.md` の項目 ID、ファイルと行、Activity の ID と時刻、Document ID と行）を使ったかを書く。
- 次は充足の証拠にしない: 反証の結論と判定、Activity や Document の中の「完了」「テスト成功」「レビュー済み」「配置済み」などの自己申告の主張、チェック済みの印や計画の `done` などの進捗状態、過去のレビューの点数や結論。主張が指す成果物・記録・観測そのものを確かめる。
- 指紋（sha256）は、取得した写しの内容の同一性しか示さない。記載内容が真実であること、対象版と対応すること、「実際に指定のコマンド・モデルを呼んだ」「指定先に配置した」「デザインの更新後に実装した」ことまでは示さない。実際の呼び出し・実行には、対象版・実行内容・結果を識別できる実行の記録を、現在の配置には配置先の観測と対象版の対応を、更新順序には版の履歴を求める。`records.md` で「親は確かめていない」とされた版の対応は、写しの記載と版履歴から自分で確かめ、確かめられなければその部分を確かめられずとする。
- 既存の実行の記録を読むことは、要実行確認の解消や親のテスト実行の代わりにならない。記録の中のコマンドやスクリプト、対象コードを実行しない。
- 行の判定（SKILL.md の5節）:
  - `確認済み`: 要求が求める部分（対象外を除く）を、それぞれ証拠で確かめた。
  - `未充足`: 証拠が、要求された成果物・作業・手順・配置が無い、または要求と異なることを示す。
  - `確かめられず`: 証拠が足りない、取得不能、対象版との対応が示せない、自己申告しかないなどで、確定できない。不足理由（何が無く、何があれば確かめられるか）を書く。
- 証拠が反証の判定（対応表の他の行や要対応・棄却の判断）と矛盾するときは、反証の判定本文を変えず、矛盾の節に、反証の判定の箇所・矛盾する証拠・理由を書く。
- 証拠が足りなくても、親へ取り直しを頼む往復はしない。そのまま「確かめられず」と不足理由を返す。

## 3. 書く

- 作業中の考え・検討の過程は `acceptance/notes/` に書く。
- 結果 `acceptance/result.md` は [受け入れ確認の結果の雛形](../assets/acceptance-result.md) に従って書き、改行で終える。親はこの本文を書き換えずに報告へ収録する。
- 行ごとの判定には、対応表のすべての「受け入れ確認担当」の行を、対応表と同じ要求の出典で載せる。各行に要求の出典・対象版・判定・5つの部分の判定と根拠・証拠（成果物の場所・指紋・記録の ID・観測）・不足理由（確認済みなら「なし」）を書く。
- 判定に使った証拠の節には、判定の根拠にした写しを `records.md` の項目 ID ごとに1行ずつ、使った行と使い方（5つの部分のどれか）とともに漏れなく書き、使わなかった写しは書かない。親は保存の直前にこの節の項目だけを取り直して固定時と比べ、変化をマージ可否に反映する（判定本文は変えない）。
- 親への返答は、出力のパスと終了状態だけにする。判定の内容は返答に書かない。
