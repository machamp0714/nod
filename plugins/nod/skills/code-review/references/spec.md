# Spec 探索の手順

この手順は、定義 `code-reviewer-spec` で起動され、依頼本文が `役割: Spec 探索` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、観点と判断基準、候補の必須項目、判定の語彙）に従う。採否・影響度・点数は決めない（反証担当と親の役割）。

## 1. 入力を確かめる

- 依頼本文の作業ディレクトリ・読んでよい入力・書いてよい場所・出力のパスを確かめる。どれかが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- 依頼本文の「担当範囲」の項目を確かめる。項目があれば、要求の範囲で2体に分けた Spec 探索の担当の1体で、値に担当（`spec1`／`spec2`）・担当範囲（要求資料の行範囲を「、」でつないだもの）・候補 ID の接頭辞（`SPC1-<n>`／`SPC2-<n>`）が書かれている（`input/target.md` の「Spec 探索の担当範囲」の節にも同じ範囲がある）。担当の要求資料は担当範囲に一部でも含まれる要求資料と、担当範囲に入れた0行の要求資料（パスの順でそれより前にある要求資料の行数の合計が `spec1` の範囲の行数より小さければ `spec1`、それ以外は `spec2`）とする。項目が無ければ、要求資料の全体が担当範囲で、すべての要求資料が担当の要求資料、候補 ID は `SPC-<n>` とする。
- `input/target.md` から対象リポジトリ（担当用の限定 clone）・mode・merge-base・head（`mode: local` では土台の HEAD と写し）・依存の写しの場所・Issue・計画の出典の扱いを読む。`input/manifest.md` の sha256 と `input/` の各ファイル（依存の写しの指紋の一覧 `deps-files.sha256` を含む）を照合し、不一致や取得できなかった資料は不足として記録する。
- 「計画の出典を解決できず不足」と書かれていれば、計画に由来するコード要求の中身を決める資料の不足として、計画が決めるはずのコード上の結論ごとに未確認の行を作り、候補を書く。別の資料で計画を補わない。

## 2. コード要求を抜き出す

- `input/requirements/` のすべてのファイル（Issue 本文・すべての `kind=spec`・計画・Workspace の規約、Issue が無ければ明示された要求）を原文のまま読む。担当範囲があっても、すべての要求資料を読んでよい。要求を読み足さない。参照先の別 Document などを辿って集めない。
- 今回の変更でコードが満たすべき要求（SKILL.md 3節の「コード要求」）だけを抜き出し、対応表の行にする。対応表の行は担当範囲の要求の分だけを書く。行は要求文・箇条・チェック項目ごとに分け、複数行の段落は1つの行にしてよい。出典は `requirements/<file>:L<開始>-L<終了>`（1行なら `requirements/<file>:L<行>`）の行範囲で書き、担当範囲の区間の中に収める（同じ要求資料で、開始と終了が区間の中）。
- コード要求でない記述（背景、作業手順の規則、ブラウザ・実環境の観測、デザインとの寸法・色・構造の一致、検査コマンドの今回の合否だけ、今回の変更の範囲外）は対応表に載せない。その分類名・件数・一覧も書かない。
- コード要求に当たるか迷う行は載せる。実行・ブラウザ・実環境で確かめる要求や「本番・承認・デザイン・画面」などの語を含む要求でも、コードで読める部分（経路・認可・入力処理・保存・migration・設定・性能上の負荷の増幅・秘密情報の流れなど）は行にして判定する（SKILL.md 3節の4つの例）。
- 担当の要求資料ごとに、担当範囲の中にコード要求が1行でもあれば「あり」、無ければ「なし」と書く。担当の要求資料でない要求資料の行は書かない。すべて「なし」なら、行の無い対応表を正常な結果として返す。
- `kind=spec` が複数あるときは、原文に書かれた適用範囲・置き換え関係で有効な要求を判別し、その根拠を書く。Document ID や日付の新しさで選ばない。補い合う関係なら併用し、置き換え関係が不明でどちらに従うか決められない矛盾は未確認とする。
- Workspace の規約（`workspace-rules.md`）のうち、今回の差分のコードが守るべき規則もコード要求として扱い、違反の候補は軸を Standards とする。規約の一覧と今回の差分への適用判断そのものは Standards 探索担当が書く。
- 計画の `done` などの進捗状態は充足の証拠にしない。

## 3. コード要求ごとに実装を確かめ、不具合を探す

- 差分は `git -C <repo> diff --no-ext-diff --no-textconv <merge-base> <head>` で読む。`mode: local` では `local/changes.diff` と `local/untracked/` を土台の HEAD に重ねて読む（必要なら自分の一時ディレクトリへ `git -C <repo> archive <sha> | tar -x -C <一時ディレクトリ>` で展開し、`git apply` で差分を当てる）。依存は適用される版の公開契約を前提に判定し、公開契約で決められない結論だけを未確認とする（SKILL.md の3節）。
- 次に読む箇所が複数決まっているときは、1ターンに複数の読み取りを並べるか、1回のシェルで複数の範囲を出して、まとめて読む（要求資料・差分・関連コードのどれでも同じ）。前の読み取りの結果で次に読む箇所が決まるときは、順に読む。まとめて読むときも、SKILL.md 2節の文脈を膨らませる読み方をしない規則（全ツリーの一括出力や大きなファイルの全文の出力をせず、パス・検索語・行範囲で絞る）に従う。
- 各行について、コード要求全体を満たす実装を固定版の証拠で確かめる。一部の証拠だけで複合要求を充足にしない。同じ語があるだけの別操作を根拠にしない。
- 未確認にしてよいのは SKILL.md 5節の4つだけで、どのコード上の結論にどの契約・資料が足りないかを書く。ブラウザ・実環境で確かめる必要があることを未確認の理由にしない。
- 正しさ・セキュリティ・性能・並行性の4観点すべてで探す。候補は担当範囲の要求を出発点に探す。主な出発点は次のとおり。
  - 要求ごとの実装: 要求された振る舞いが、すべての経路で実装されているか。
  - 境界条件: 空・最大・重複・未設定・既存データなど、要求が及ぶ入力の端で破綻しないか。
  - 異常系: 失敗・中断・再実行・取得できない場合に、要求された扱いになるか。
  - 要求された性能・権限・同時操作: 要求が求める規模・権限の範囲・同時実行で成り立つか。
- 関連コード（呼出元・呼出先・状態の保存先・防御・公開契約・テスト）も固定版で読む。性能は実在する入力規模・処理の増幅・要求との関係を、並行性は到達可能な実行順序と破綻を証拠に示す。
- 候補の「契約の出典」と「関連する要求・契約」には、担当範囲の外の要求を挙げてよい。担当範囲の外の要求だけを破る不具合に気づいたときも候補にしてよいが、その要求の対応表の行は作らない。
- 見つけた不具合が要求ではなく規約・既存の契約・一般的な不具合を破るなら、軸は Standards とし、候補 ID は自分の接頭辞（`SPC-<n>`、分けたときは依頼本文の `SPC1-<n>` か `SPC2-<n>`）のまま書く。

## 4. 書く

- 作業中の考え・読んだ箇所の控え・検討の過程は、依頼本文の書いてよい場所の `notes/`（`spec/notes/`、分けたときは `spec1/notes/` か `spec2/notes/`）に書く。
- 引き渡し用ファイル（依頼本文の出力。`spec/handoff.md`、分けたときは `spec1/handoff.md` か `spec2/handoff.md`）は [Spec 探索の雛形](../assets/spec-handoff.md) に従って書く。要求資料ごとのコード要求あり／なしの表と、充足の行を含むコード要求の対応表（要求の出典・状態・証拠または不足理由・候補ID の4列。状態は 充足／未充足／未確認）を書く。未充足・未確認の行には対応する候補を書く。候補 ID は依頼本文の接頭辞で付ける（分けないときは `SPC-<n>`、分けたときは `SPC1-<n>` か `SPC2-<n>`）。
- 「充足」の行は、同じ要求資料の連続する要求をまとめて1行に書いてよい。出典は1つ以上の行範囲（例: `requirements/spec-1.md:L10-L14`、`requirements/spec-1.md:L16-L20`）で書き、証拠の欄は固定版の場所（`<path>@<sha>:L<開始>-L<終了>`）を並べるだけにして説明文を書かない。まとめても充足の確かめ方は変えない（3節。要求ごとにコード要求全体の充足を固定版の証拠で確かめ、複合要求を一部の証拠で充足にしない）。
- 「未充足」「未確認」の行は1要求1行（行範囲は1つ）で書く。根拠は今までどおり、未充足は満たされない部分・固定版の場所・候補 ID、未確認は SKILL.md 5節の4つの理由のどれか・どのコード上の結論にどの契約や資料が足りないか・不足箇所・候補 ID を書く。
- 要求の出典は行の間で重複させない（同じ範囲の要求は1行にまとめる）。反証は「充足」の行の証拠を確かめ直さないので、「充足」は確かめた行だけに付ける。
- 暫定の重大度・確信度・要約・推論・総合判断・原因の統合を書かない。
- 候補が無ければ「候補0件」と明示する。コード上の結論に必要な資料が足りず確かめられなかった点は、部分レビューへ縮小せず、未確認として理由と不足箇所を書く。
- 書き終えたら、禁止項目が無いこと、担当の要求資料だけにコード要求あり／なしがあること、要求の出典が行範囲の形で行の間で重複せず担当範囲の中にあること、未充足・未確認の行が1要求1行であること、未充足・未確認の行の候補 ID が候補一覧にあること、候補 ID が自分の接頭辞であることを自分で見直す。コード要求の取り落としが無いかは担当範囲の原文を読み直して確かめる（親のスクリプトの検査は形式だけで、取り落としを見つけない）。
- 親への返答は、出力のパス・終了状態（完了／未確認を含む）・候補の件数・対応表の行数だけにする。候補の内容や見立ては返答に書かない。
