# Spec 探索の手順

この手順は、定義 `code-reviewer-spec` で起動され、依頼本文が `役割: Spec 探索` を指定したときだけ使う。
SKILL.md の共通規則（権限と資料の境界、観点と判断基準、候補の必須項目、判定の語彙）に従う。採否・影響度・点数は決めない（反証担当と親の役割）。

## 1. 入力を確かめる

- 依頼本文の作業ディレクトリ・読んでよい入力・書いてよい場所・出力のパスを確かめる。どれかが欠けていれば、何も書かずに「入力不備: <理由>」を返して終了する。
- `input/target.md` から対象リポジトリ・mode・merge-base・head（`mode: local` では土台の HEAD と写し）・Issue・計画の出典の扱いを読む。`input/manifest.md` の sha256 と `input/` の各ファイルを照合し、不一致や取得できなかった資料は不足として記録する。
- 「計画の出典を解決できず不足」と書かれていれば、計画に由来する要求は確かめられないものとして対応表に未確認の行を作り、候補を書く。別の資料で計画を補わない。

## 2. 要求を確認単位に分ける

- `input/requirements/` のすべてのファイル（Issue 本文・すべての `kind=spec`・計画・Workspace の規約、Issue が無ければ明示された要求）を原文のまま読む。要求を読み足さない。
- 見出し・空行・書式だけの行を除くすべての行を、どれかの確認単位の行範囲に含める。確認単位は要求文・箇条・チェック項目ごとに分け、複数行の段落は1つの単位にしてよい。出典は `requirements/<file>:L<開始>-L<終了>` で書く。
- `kind=spec` が複数あるときは、原文に書かれた適用範囲・置き換え関係で有効な要求を判別し、その根拠を書く。Document ID や日付の新しさで選ばない。補い合う関係なら併用し、置き換え関係が不明な矛盾は未確認とする。
- Workspace の規約（`workspace-rules.md`）も確認単位に含める。今回の差分に関係しない単位は理由を付けて「対象外」、守られているかを確かめた単位は他の要求と同じ状態にし、違反の候補は軸を Standards とする。規約の一覧と今回の差分への適用判断そのものは Standards 探索担当が書く。未登録と書かれていれば、その旨の1行を「対象外」とする。
- 背景・根拠・範囲宣言だけの単位は「説明」、書式や検査コマンドの合否だけを求める単位は「自動チェック担当」とする。義務が混ざる単位を説明にしない。計画の `done` などの進捗状態は充足の証拠にしない。

## 3. 要求ごとに実装を確かめ、不具合を探す

- 差分は `git -C <repo> diff <merge-base> <head>` で読む。`mode: local` では `local/changes.diff` と `local/untracked/` を土台の HEAD に重ねて読む（必要なら自分の一時ディレクトリへ `git -C <repo> archive <sha> | tar -x -C <一時ディレクトリ>` で展開し、`git apply` で差分を当てる）。対象の作業ツリーは読まない。
- 各確認単位について、要求全体を満たす実装を固定版の証拠で確かめる。一部の証拠だけで複合要求を充足にしない。同じ語があるだけの別操作を根拠にしない。
- 正しさ・セキュリティ・性能・並行性の4観点すべてで探す。主な出発点は次のとおり。
  - 要求ごとの実装: 要求された振る舞いが、すべての経路で実装されているか。
  - 境界条件: 空・最大・重複・未設定・既存データなど、要求が及ぶ入力の端で破綻しないか。
  - 異常系: 失敗・中断・再実行・取得できない場合に、要求された扱いになるか。
  - 要求された性能・権限・同時操作: 要求が求める規模・権限の範囲・同時実行で成り立つか。
- 関連コード（呼出元・呼出先・状態の保存先・防御・公開契約・テスト）も固定版で読む。性能は実在する入力規模・処理の増幅・要求との関係を、並行性は到達可能な実行順序と破綻を証拠に示す。
- 見つけた不具合が要求ではなく規約・既存の契約・一般的な不具合を破るなら、軸は Standards とし、候補 ID は `SPC-<n>` のまま書く。

## 4. 書く

- 作業中の考え・読んだ箇所の控え・検討の過程は `spec/notes/` に書く。
- 引き渡し用ファイル `spec/handoff.md` は [Spec 探索の雛形](../assets/spec-handoff.md) に従って書く。要求ごとの対応表は、充足の行を含む全行を4列（要求の出典・状態・証拠または不足理由・候補ID）で書く。未充足・未確認の行には対応する候補を書く。
- 暫定の重大度・確信度・要約・推論・総合判断・原因の統合を書かない。
- 候補が無ければ「候補0件」と明示する。必須の資料が足りず確かめられなかった点は、部分レビューへ縮小せず、未確認として理由と不足箇所を書く。
- 書き終えたら、禁止項目が無いこと、全確認単位を覆っていること、未充足・未確認の行の候補 ID が候補一覧にあることを自分で見直す。
- 親への返答は、出力のパス・終了状態（完了／未確認を含む）・候補の件数・対応表の行数だけにする。候補の内容や見立ては返答に書かない。
