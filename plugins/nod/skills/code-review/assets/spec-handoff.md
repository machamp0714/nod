# Spec 探索の引き渡し

## 担当と対象

- 役割: Spec 探索
- 定義名: code-reviewer-spec
- 担当 ID: （分かれば。分からなければ「不明」）
- モデル申告: （自分で分かる情報と出典。分からなければ「未確認」）
- 対象版: 対象リポジトリ（`target.md` の担当用の限定 clone）の絶対パス／mode／merge-base の SHA／head の SHA（mode: local なら土台の HEAD と `local/` の各ファイルの sha256）。merge-base と head の40桁の SHA は両方ともこの欄に書く（基点など別の欄に書いた SHA は数えない）
- 要求資料: 読んだ `requirements/` のファイルと、`manifest.md` の sha256 との一致。計画の出典の扱い（写しあり／計画の出典なし／解決できず不足）
- 依存の写し: `target.md` が示す場所、`manifest.md` の lockfile のパスと sha256、`deps-files.sha256` と `manifest.md` の sha256 との一致（準備されていなければ「依存の写しなし」と `manifest.md` の理由）
- 終了状態: 完了／未確認を含む（未確認の内容は下の節）

## 要求資料の判別

`kind=spec` が複数ある場合の適用範囲・置き換え関係と、その原文の出典。併用する資料、未確認とした矛盾。該当しなければ「該当なし」。

## 要求資料ごとのコード要求

`requirements/` のすべてのファイルを1行ずつ書き、今回の変更でコードが満たすべき要求（コード要求）が1行でもあれば「あり」、無ければ「なし」とする。補足が要るときは値の後ろに括弧1つで書く（例: `なし（作業規約の登録が無い）`）。括弧の補足は判定に使わず、補足の後ろに値や文を続けない。分類名・件数・範囲外の一覧は書かない。

| 要求資料 | コード要求 |
|---|---|
| `requirements/<file>` | あり／なし |

## コード要求の対応表

コード要求だけを1行ずつ書く。状態は 充足／未充足／未確認 のどれか。未確認の不足理由には、どのコード上の結論にどの契約・資料が足りないかを書く。コード要求が0件なら、見出しの行と区切りの行だけの表にする。

| 要求の出典 | 状態 | 証拠または不足理由 | 候補ID |
|---|---|---|---|
| `requirements/<file>:L<開始>-L<終了>` | | | |

## 候補

候補が無ければ、この節に「候補0件」とだけ書く。

### SPC-1

- 軸: Spec／Standards
- 場所: `<path>@<sha>:L<開始>-L<終了>`（実装が無いことが不具合なら、あるべき箇所と要求の出典）
- 起点: 今回の差分／基点から存在
- 到達条件:
- 期待動作:
- 破綻:
- 影響:
- 証拠: 固定版と要求の出典、そこから読み取れる事実（性能は実在する入力規模・処理の増幅・要求との関係、並行性は到達可能な実行順序と破綻。基点から存在なら merge-base の同じ内容。証拠を取得できなかったときは理由と不足箇所を、この欄か、同じ候補の `- 取得できなかった理由:`・`- 不足箇所:` の項目に書く。ほかの候補・節の記述は数えない）
- 契約の出典: （破った要求・規約・既存の契約の出典）
- 関連する要求・契約: （軸と別の契約も破る場合の出典。なければ「なし」）

## 探索上の不足・未確認

読めなかった資料、確かめられなかった点、理由と不足箇所。なければ「なし」。

## 判断を見送った事項

1件ごとに短い理由。なければ「なし」。
