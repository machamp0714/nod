# nod:implement

Issue の要求を最後まで実装する。既存の計画（`nod:to-plan` で作った Task と Step）があれば依存の順に使い、なければ本文を正本に必要な作業だけを追跡する。途中でユーザーの確認を挟まない。中断しても、nod の Step の状態と作業ログから別の LLM が再開できるように記録を残す。

引数: `<Issue id>`（必須）。

## 0. 準備

- Codex で動いているときは、nod に書き込む前に `export NOD_ACTOR=codex` を実行する。
- **デフォルトブランチ（main / develop など）の上なら、何もせずに止めて**、作業ブランチを作るよう伝える（`nod issue branch-name <id>` で候補が得られる。GitHub に出るブランチ名・コミット・PR には nod の Issue ID を書かない）。判定状態や needs-spec による停止は以下に従う。
- 作業ツリーに、この Issue と関係のない未コミットの変更があれば触らない（stash もしない）。コミットには自分の変更だけを入れる。
- **start より先に** `nod issue show <id> --json` で本文、ラベル、`specAssessment`、計画（Task・Step の状態）、Documents、Activity（作業ログ）を読む。kind=spec の Document があれば全文読む。
- Issue の Workspace で `nod workspace spec-assessment show --json` を読み、現在の `enabled` を確認する（別 Workspace の Issue は、その Workspace を指定して確認する）。
- Workspace が有効で、`specAssessment` があり、`status` が `pending` または `failed`、かつ `suspended` でも `recordOnly` でもない場合は、`nod issue assess <id> --json` で初回判定の回復を **1 回だけ**試み、`show --json` で状態を再確認する。まだ実効的な未完了・失敗なら、作成済みの同じ ID と安全な失敗種別を報告して止める。Issue を作り直さず、秘密値や未加工の API エラー本文を出さない。
- `specAssessment` がない（null／省略）場合は対象外、`suspended` は Workspace の無効化による制限解除、`recordOnly` は初回判定後の任意再評価である。これらの履歴上の待機・失敗で実装を止めない。設定の無効化やラベル削除を LLM が制限回避のために行わない。
- 現在のラベルに `needs-spec` があれば、`nod:to-spec <id>` へ案内して実装を始めずに止める。仕様書があっても同じ。`nod:to-spec` は仕様書の作成・添付の完了を確認して解除する。`nod:implement` 自身は解除しない。
- `needs-spec` がなく判定完了済み（任意再評価中も含む）または対象外・制限解除済みなら `nod issue start <id>` を実行する。追加指示が出たら先に読んで反映する。
- spec・plan・事前の `nod:to-plan` は必須にしない。既存 spec と計画は引き続き使う。spec がなければ Issue 本文の要求と完了条件を正本にする。見出しやチェックボックスの有無、短文であることだけで仕様不足と決めない。
- 計画がなければ本文から実装・検証できる範囲の軽い Task・Step を作業追跡用に記録する（例: `nod issue plan <id> --step "本文の要求を実装・検証する"`）。計画 Document の作成や別工程の承認を増やさない。重要な利用者向け仕様を決めないと進められない場合だけ、未決事項を `nod issue ask` に記録して止める。

## 1. 再開位置を決める

- 状態が done / skipped の Task は飛ばす。
- doing の Task があれば、中断した作業である。作業ログの最後の記録と `git log` / `git status` を見て、どこまで進んだかを確かめてから続ける。
- 依存先（Task タイトル末尾の「依存: …」）がすべて done の Task のうち、番号の小さいものから進める。

## 2. Task を 1 つずつ実装する

各 Task について次を行う。

1. `nod issue step <id> <N> doing` にする。
2. **新しいエージェントに任せる。** ハーネスにサブエージェントがあれば、Task ごとに新しいものを起動する（前の Task の文脈を持ち込まない）。無ければ、このセッションで順に実装する。渡す内容:
   - Issue id、Task N のタイトルと Step（受け入れ条件）、仕様書のパス（なければ Issue 本文の全文と、それが正本であること）
   - 仕様の Testing Decisions に書かれた seam で、Skill ツールの `tdd` を使ってテスト先行で実装すること（合意済みの seam は確認し直さない）。仕様書がなければ本文の完了条件と既存テストを基に、外から観測できる既存の境界で検証し、その選択を記録する
   - 型チェック（あれば）と単体のテストファイルをこまめに実行すること。テストの実行方法はリポジトリの CLAUDE.md / AGENTS.md に従う
   - コミットしないこと、`nod:implement` / `nod:code-review` を呼ばないこと、エージェントを増やさないこと
   - 終わったら、変えた内容・実行したテストと結果・判断したこと・残った懸念を報告すること
3. 結果を確かめる。差分が Task の範囲に収まっているか、Step を満たしているかを見る。足りなければ同じ Task を続けさせる。
4. 満たした Step を `nod issue step <id> <N.M> done`、Task を `nod issue step <id> <N> done` にする。満たせなかった Step は skipped にせず doing のまま残し、ログに理由を書く。
5. **コミットする。** メッセージはリポジトリの既存のコミットの書き方に合わせる。nod の Issue ID は書かない。対応する GitHub Issue がコードと同じ repo にあるときだけ、作業が済んだ最後のコミットに `Fixes #<GitHub の番号>` を付ける（途中のコミットには付けない）。
6. **作業ログを残す**（引き継ぎの正本）。
   - `nod issue log <id> "Task N 完了: <何ができたか>。コミット <短い sha>。次: Task M" --kind progress`
   - 実行したテストと件数・成否を `--kind test` で 1 件
   - 選んだ案と理由があれば `--kind rationale`
   - ログは要点だけにする（1 件 4000 字まで）。秘密値は書かない。

### 詰まったとき

- 仕様で決まっていない判断は、仕様と既存コードに最も沿う案を選んで進め、`--kind rationale` に残す。ユーザーに止めて聞くのは、どの案を選んでも仕様を満たせないときだけ（`nod issue ask <id> "<質問>"`）。
- 進められない Task は `--kind blocker` に原因と必要なものを残し、その Task に依存する Task も飛ばす。依存しない Task は続ける。

## 3. 仕上げ

1. **最後のコミットの後、[親用の参照ファイルの0.1節](../code-review/references/parent.md#01-通常レビューも隔離した親から開始する)に従い、新しい隔離親セッションへ独立レビューを1回依頼する。** この実装セッションから3担当を直接起動しない。空 cwd・`--no-context-files --no-rules`・新しい session-dir を使い、対象・基点・head・Issueだけを引き継ぐ（実装報告・作業ログ・テスト結果・過去レビュー・会話履歴は渡さない）。起動済みの親の結果を待ち、二重起動しない。起動できなければ未実施として報告し、直接委譲で代替しない。
   - 対象は現在の HEAD commit（`mode: commit`）、基点はデフォルトブランチとの merge-base、要求はこの Issue（本文、リンクされたすべての kind=spec の Document、`plan.source` が指す kind=plan の Document、Workspace の規約）。これらは実装工程から引き継いだ情報であり、聞き直さない。Spec 軸は省略しない。
   - 親は自分でレビューしない（書いたセッションの確証バイアスを避けるため）。役割別の3定義（`code-reviewer-standards`・`code-reviewer-spec`・`code-reviewer-refute`）へ委譲する。使えなくても旧 `code-reviewer` やバンドル済みの `reviewer` で代用しない。このレビューはコードレベルの確認であり、ブラウザ検証・見た目やデザイン・実環境での動作・作業手順は確かめない（親の手順のとおり）。この Issue の作業手順の責務（独立レビュー、PR の統合先、本人の確認、本番操作の権限など）は、この手順の2〜4節と依頼範囲で従来どおり守る。
2. 仕上げでテストスイート全体を手元で回さない（親もテスト・Lint を実行しない）。Task 中の型チェック・単体のテストファイルの実行（2節）は従来どおり行う。
3. 報告は親用の参照ファイルどおり、親の手順の10節・11節の `review.ts finalize` で結果と監査の kind=doc の Document として Issue に添付し、作業ログに要約と Document ID を残す（完了は `--kind progress`、未実施・未完了は `--kind blocker`。スクリプトが書く）。merge-ready の付け外しとその理由・判定した head SHA・現在の head と基点の照合も、スクリプトが本文を `[merge-ready]` で始めて `--kind progress` に1件残す。報告の保存後にこの Issue へ書く作業ログ・コメント（PR の URL、提出の記録などを含む）は通常どおり書き、id を記録・受け渡ししない。
4. 最終状態・確認が残る事項で後続を分け、マージ可否は記録・報告して merge-ready にだけ使う。マージ可否は、最終状態が完了・確定した要対応0件（点数 5）・確認が残る事項0件・現在の head がレビューした head と同じ・現在の基点がレビューした基点と同じ、の5条件だけで決まる（親の手順の10節の8・11節）。CI の結果はマージ可否に含めず、CI が落ちた PR のマージを止めるのは GitHub の必須ステータスチェック（ブランチ保護・ルールセット）に任せる。
   - **未実施**（担当を1つも起動しなかった: 委譲できない環境、差分なし、秘密情報を含み得るファイル、担当用の限定 clone を作れない）と**未完了**（3担当のどれかの有効な結果が無い。利用枠の上限で止めた場合と、判定と無関係な無効で親の手順どおり1回だけ委譲し直した後も有効な結果が無い場合。探索の片方が無効で反証へ進めない場合を含む）: blocker を記録し、Done・In Review・PR に進めない（PR 不要の依頼でも Done にしない）。親の手順内の1回限りの再委譲のほかに、さらに委譲し直したり、利用枠の回復を待って流し直したり、別のアカウント・モデルへ切り替えたりせず、自分でレビューして補わない。
   - **完了でもマージ可否が不可**（確認が残る事項がある、確定した要対応の点数が 5 未満、現在の head または基点がレビューした版と違う）: レビューの原文・最終状態・点数を変えずに結果を記録し、6・7 の提出・完了条件へ渡す。確認が残る事項（要求の出典・確かめる担当・理由。コードレベルで結論を出せない未確認（コード要求の中身を決める要求資料の不足・結論に必要な依存の契約の不足・要求間の矛盾・採否を確定できない候補）と、保存直前の再照合で見つかった要求資料・未コミット変更の変化）は必要な検証が終わっていないものとして扱い、合格・指摘なし・確認済みへ読み替えず、提出と完了（Done・In Review・PR）を止めて事項と再開条件を記録する。このレビューの判定を書き換えず、確かめ直すには新しいレビューを行う（親の手順の12節）。新しい head・基点のマージ可否は、新しいレビューでだけ決まる。
5. レビューの指摘は直さない。報告に載せる（何度回しても新しい指摘が出るので、自動で直すと終わらない）。
6. Task・Stepと必要な検証が完了したら、独立コードレビューの結果（報告 Document ID）を作業ログと報告に残す。PRを含む依頼では、既存の指摘対応・提出条件を満たしてPRを作成・紐付けし、レビュー依頼時に `nod issue update <id> --status in_review` で In Review に移す。CI の結果を待つ・照合する・記録する手順は置かない。PM等の後続PR依頼待ちなら実装結果を報告して待ち、先にDoneにしない。マージ可否が「可」でも、既存のマージ条件と依頼範囲は変えない。merge-ready ラベルは親の手順（10節・11節）の判定だけで付け、実装の手順から直接付けない（外すのは下の提出時の照合と4節の再開時）。ラベルを自動マージ・承認の代わりにしない。
   - **提出時の merge-ready の照合**: PR を作成・更新して提出するとき（再提出を含む）に merge-ready が付いていれば、ラベルを付けた最新の `[merge-ready]` の作業ログ（親の手順の11節）の「判定した head SHA」と「レビューした基点」を、`gh pr view <PR> --json headRefOid,baseRefName` で読んだ現在の PR の `headRefOid` と `baseRefName` に比べる。head が違う（判定が古い（追加コミット））、基点が違う（基点が変わった）、記録が無い・読めない・レビューした基点がブランチ名でない（記録の不足）、PR の head か基点を読めない（照合できない）なら、`nod issue update <id> --remove-label merge-ready` で外し、理由・判定した head SHA・現在の head・レビューした基点・現在の基点を、本文を `[merge-ready]` で始めて `--kind progress` に1件記録する。同じなら付けたままにする。この照合からはラベルを付けない（新しい head・基点のマージ可否は新しいレビューでだけ決まる）。
   - **必須チェックの設定の報告**: PR の作成・提出の報告の前に、PR の `baseRefName` のブランチの必須チェックの設定を読み取る（`gh api repos/{owner}/{repo}/branches/{base}` の `.protected` と `.protection.required_status_checks`、`gh api repos/{owner}/{repo}/rules/branches/{base}` の `required_status_checks` の規則）。結果は次のどれか1つとして報告に書く。これは報告事項で、マージ可否・merge-ready・In Review・Done の条件にしない。
     - 設定あり（必須チェックを1件以上読めた）: チェック名と、読めた出典（ブランチ保護・ルールセット）。片方を読めなかったなら、そのことも書く。
     - 未設定（両方を読めて、保護なし、または保護の必須チェックが0件か強制が off で、ルールセットにも必須チェックが無い）: 「このリポジトリは必須チェックが設定されておらず、CI が落ちていても GitHub はマージを止めない」。
     - 確認できない（認証・権限・通信の失敗、JSON でない・想定外の形、保護ありで必須チェックの設定が見えない、のどれかがあり、必須チェックを1件も読めなかった）: 設定を読めず、設定の有無を確認できないことと、その理由。読めないことは未設定を示さないので、未設定の文は書かない。
7. PRを含む依頼は、mergeとIssueの完了条件（検証・反映など）を確認した人または権限のあるエージェントが `nod issue done <id> --summary "<実装内容と検証結果>"` で明示的にDoneにする。PR不要の依頼は必要な検証と完了条件を満たして直接Doneにできる。人間承認の新たな必須条件は設けず、PR作成・承認・merge・本番反映の権限は既存の依頼範囲を守る。merge する場合も、GitHub の必須ステータスチェック・ブランチ保護・ルールセットを回避しない（`gh pr merge --admin` を使わない、保護やルールセットを一時的に外さない、必須チェックを迂回する手段を使わない）。merge の前にも6と同じく必須チェックの設定を読み取り、設定あり・未設定・確認できないのどれかを報告に書く。

## 4. 報告と完了時のネクストアクション

終えた Task・飛ばした Task とその理由・テストの結果・独立コードレビューの指摘・Issueの完了状態を簡潔に報告する。
独立コードレビューは、結論（最終状態・点数・マージ可否・merge-ready）、Severity付きの要対応、未確認の不足と担当、結果Document IDと監査Document IDだけを簡潔に報告する。担当別の原文・全対応表・指紋・担当ID・試行の詳細は監査Documentを参照し、チャットへ転載しない。点数はマージ許可を意味しない。
PRの作成・提出・mergeを報告するときは、基点ブランチの必須チェックの設定を読んだ結果（設定あり・未設定・確認できない）を添える（3節の6・7）。読めないときは未設定と書かず、設定の有無を確認できないことと理由を書く。
未完了のTaskや失敗した必要テスト、未実施・未完了の独立レビュー、確認が残る事項が残る場合はdoneにせず、原因と再開条件を記録する。
人によるnodの承認待ちは設けない。

次の作業がある場合だけ、具体的な選択肢を番号付きで示し、おすすめを理由つきで添える。
コードレビューの指摘対応や、依頼範囲に含まれていなかったPR作成は独立した次の作業として扱う。
PR作成を依頼されたら、タイトル・本文にnodのIssue IDを書かず、作成後に`nod issue link-pr <id> <URL>`で紐付ける。完了後に別途依頼された場合も、レビュー依頼時に明示的にIn Reviewへ戻す。提出しただけではDoneにしない。
指摘対応は`nod issue start <id>`でIn ReviewからIn Progressへ再開し、既存の着手条件を守る。再開時や新しいコミットを足すときに merge-ready が付いていれば、`nod issue update <id> --remove-label merge-ready` で外し、理由（追加コミットで判定が古い）と判定した head SHA を、本文を `[merge-ready]` で始めて `--kind progress` に記録する。新しい head の merge-ready は、その head に対する新しいレビュー（親の手順）の判定でだけ付く。draftは原則In Progress、mergeせずcloseして継続するならIn Progress、中止なら理由付きCanceled、後回しならTodo/Backlogへ明示的に移す。reopen後はレビューならIn Review、修正ならIn Progressにする。
PRの作成・紐付け・状態取得・取得失敗・merge・close・reopenでIssueの状態は自動変更されない。
