# nod:to-spec

nod の Issue 1 件を対象に、未決の論点を grilling で詰め、仕様書を書いて Issue に添付する。

引数: `<Issue id>`（必須）。任意で照会先のモデルと effort（例: `--reviewer-model gpt-6-astra --reviewer-effort high`）。

## 0. 準備

- Codex で動いているときは、nod に書き込む前に `export NOD_ACTOR=codex` を実行する。
- `nod issue show <id>` で説明・Documents・Activity を読む。既に kind=spec の Document があれば、作り直すのか追記するのかをユーザーに聞く。
- リポジトリを調べる。`CONTEXT.md` があれば用語をそれに合わせ、触る領域の ADR を守る。

## 1. 前提を決める

- **Issue 本文に明記されている内容（例文・決定事項・受け入れ条件）は前提であり、論点にしない。** 変えたほうがよいと思ったら「Issue の記述を変える提案」と明示して別に出し、照会先と一致しても勝手に確定させない。
- **問いと答えの記録を、最初から nod の Document にする。** 一時ディレクトリに置くと、セッションの再開などで消えて原文が残らないため。grilling を始める前に `nod doc list` で同名が無いことを確かめ、`nod doc create <id を小文字にしたもの>-grilling-YYYYMMDD.md --title "<id> grilling の問いと答え" --kind doc --issue <id> --body "<冒頭の説明>"` で作って添付する。冒頭の説明には、照会先のモデル・effort と、Issue 本文を前提として問わないことを書く。
- この Document（作られた Markdown ファイル）が決定ログを兼ねる。以後はファイルを直接編集して、ラウンドごとに追記する（`nod doc create` は既存のファイルを上書きしないので、作り直さない）。

## 2. grilling（別モデルとの照合つき）

Skill ツールで `grilling` を呼び、その手順（設計の木、frontier、ラウンド制、各問に推奨を添える）に従う。各ラウンドを次のように進める。

1. **自分の推奨を先に固定する。** frontier の質問と自分の推奨・理由をファイルに書く。事実が要る問いは、推奨の前にコードで確かめる。
2. **もう一方のモデルに独立に答えさせる。** 推奨を取り除いた質問だけを、Issue 本文と決定ログと一緒に渡す。プロンプトには次を入れる。
   - Issue 本文と決定ログは確定事項で、覆さないこと（懸念は「変更の提案」と明示して別に書く）
   - 各問に「回答（選択肢の記号か独自案）・理由・根拠（file:line、調べていなければ『推測』）」で答えること
   - 確かめてほしい事実（あれば）
   - 最後に「まだ決まっていない論点」を最大 3 つ。実装者が決めてよい細部は挙げない
3. **突き合わせる。** 一致した問いは確定として扱う。割れた問いだけを、両方の案・根拠・自分の推奨（照会先の根拠で考えが変わったらそう書く）を添えてユーザーに聞く。照会先が示した事実は、判断に使う前に自分でも確かめる。
4. **ラウンドの記録を Document に追記する。** ユーザーの回答が出そろったら、`## Round N` の見出しの下に、問いごとに「問い・自分の推奨・照会先の回答・決定・決定者（一致／ユーザー／差し戻し）」を表で書く。照会先の回答の原文は、`<details>` に折りたたんでそのまま貼る。前提の訂正や、決定の見直し（どの問いを、なぜ変えたか）もここに書く。
5. 照会先が挙げた新しい論点は、次のラウンドの候補にする。ユーザーの回答で前提が変わったら、その影響を受ける問いを見直す。
6. frontier が空になり、ユーザーが合意を確認したら終える。合意したテストの seam（3）も Document に追記する。

照会先は「いま動いていないほうのモデル」にする。

- Claude Code から: `codex exec -m <model> -c model_reasoning_effort=<effort> -s read-only --skip-git-repo-check -o <回答ファイル> - < <プロンプトファイル>`（既定は gpt-6-astra・high。バックグラウンドで実行するときも標準入力をファイルから渡す。渡さないと入力待ちで止まる）
- Codex から: `claude -p --permission-mode plan --model <model> < <プロンプトファイル> > <回答ファイル>`（既定は opus）

## 3. テストの seam を確認する

テストする境界（seam）を書き出し、ユーザーに確認する。既存の seam を優先し、できるだけ高い層に置き、数は少なく（理想は 1 つ）。各 seam に、手本になる既存のテストを添える。

## 4. 仕様書を書く

本文（新規・作り直し・追記）は主担当（このスキルを動かしているエージェント）が書く。執筆ルールと仕様書テンプレートは `references/spec-writing.md`（このスキルのディレクトリ内）が正本で、執筆と照合に使う。日本語の執筆・推敲は、利用者の常設指示（`CLAUDE.md` や `AGENTS.md` などのグローバルな指示）に従う。

1. **入力を選び、控えを残す。** 執筆に使うのは次の入力。
   - Issue 本文
   - 決定ログ（§1 の Document）
   - 関連する既存の正式仕様書: 主担当が選ぶ。Issue 本文や決定ログが明示的に参照する Issue の kind=spec の Document
   - 作り直し・追記では、改訂の対象の仕様書
   - **書き始める前に**、選んだ関連 Document（ID・題・選んだ理由。無ければ「なし」）と改訂の対象を決定ログの末尾に書く。
   - 続けて、執筆に使う版の控えを、決定ログと同じディレクトリの新しい控えのディレクトリ `<id を小文字にしたもの>-spec-inputs-YYYYMMDDHHMM/` に残す（既存なら別名にし、上書きしない）。Issue 本文は `set -o pipefail; nod issue show <id> --json | jq -ej 'select(has("id")) | .description // ""' > <控えのディレクトリ>/issue.txt` で残す（本文が無い Issue では空の控えになる）。決定ログ・関連仕様・改訂の対象は、それぞれのファイルを `cp` で控えのディレクトリへ写し（名前が重なれば別名にする）、元の絶対パスと写しの名前を `<控えのディレクトリ>/sources.txt` に 1 行ずつ書く。どれかの終了コードが 0 でなければ（Issue を取得できなかった場合を含む）その控えを使わず、取り直す。以後、§5 の 2 で仕様書を書き込むまで決定ログを書き換えない。
   - **執筆と照合には控えだけを使う。** Issue 本文・決定ログ・関連仕様・改訂の対象は控えのディレクトリの写しから読み、元のファイルや、控えより前（§0〜§3 を含む）に読んだ内容で書かない。元のファイルがその後に変わったかは、§5 の 1 で写しと比べて確かめる。
2. **原稿をファイルに書く。** `references/spec-writing.md` に従って書き、決定ログと同じディレクトリに `<id を小文字にしたもの>-spec-draft-YYYYMMDDHHMM.md` として保存する（既存ファイルがあれば別名にし、上書きしない）。推敲で最終稿が別のファイルになったら、以後の照合・添付にはその最終稿を原稿として使う。
3. **原稿を照合する。** 原稿を決定ログと `references/spec-writing.md` に照らし、次を確かめる。
   - 決定ログのすべての決定と合意したテスト seam が反映されている
   - 新しい決定が足されていない。不採用案や未確認の情報が決定として書かれていない
   - 決定事項・条件・例外・義務と許可・推量の強さが決定ログと変わっていない（推敲で「してよい」が「する」になるような変化を含む）
   - テンプレートの 7 節がそろう（追記では不要）
   - ファイルパスとコード片が無い
   - 冒頭に、Issue 本文が前提であること・照合の経緯・執筆者がある（追記では追記部分の執筆者）
4. **食い違いは主担当が原稿を直し、3 をやり直す。** 推敲の検査の指摘が決定ログと食い違うときは、決定ログに合わせる。
5. **未決の点に気づいたら**、推測で埋めず、§2 の grilling の新しいラウンドに戻り、決まってから 1 からやり直す（控えも取り直す）。
6. **照合を終えたら、原稿の末尾を改行にそろえ、原稿の指紋を残す。** 末尾が改行でなければ `[ -z "$(tail -c 1 <原稿>)" ] || printf '\n' >> <原稿>` で改行を 1 つ足す。`nod doc create` は改行で終わらない本文の末尾に改行を補うため、添付後の本文の指紋を原稿とそろえる。続けて `shasum -a 256 <原稿の絶対パス> > <控えのディレクトリ>/draft.sha256` で、照合を終えた原稿の指紋を残す。以後、原稿は変えない。変えたときは 3 からやり直し、指紋も取り直す。

## 5. Issue に添付する

1. **入力と原稿が変わっていないことを確かめる。** 添付の直前に、`set -o pipefail; nod issue show <id> --json | jq -ej 'select(has("id")) | .description // ""' | cmp - <控えのディレクトリ>/issue.txt`、`sources.txt` の各行についての `cmp <元のファイル> <控えのディレクトリ>/<写し>`、`shasum -a 256 -c <控えのディレクトリ>/draft.sha256` が、すべて終了コード 0 で終わることを確かめる。1 つでも 0 でなければ（Issue を取得できなかった場合を含む）原稿を採用しない。取得の失敗なら、取得できるようになってから 1 をやり直す。入力が変わっていたら、§4 の 1 から新しい控えでやり直す（作り直し・追記では更新後の改訂の対象を使う）。原稿だけが変わっていたら、§4 の 3 から照合し直す。
2. 執筆の種類ごとに添付する。§4 の 6 を終えた原稿を変えずに使う。
   - **新規:** `nod doc list` で同名のファイルがないことを確かめる（`nod doc create` は既存ファイルを上書きしない）。`nod doc create <id を小文字にしたもの>-spec-YYYYMMDD.md --title "<id> 仕様: <短い題>" --kind spec --issue <id> --body - < <原稿>` で作って添付する。
   - **作り直し:** 既存の仕様書の 1 行目がタイトル見出し、2 行目が空行であることを確かめる。改訂前の写しを同じディレクトリに保存する（`<元のファイル名>-before-YYYYMMDDHHMM.md`。既存ファイルがあれば別名にし、上書きしない）。`{ head -n 2 <改訂前の写し>; cat <原稿>; } > <仕様書のパス>` でタイトル見出しの後を原稿の全文に置き換える。kind と Issue リンクはそのまま保つ。
   - **追記:** 作り直しと同じ要領で改訂前の写しを保存し、既存の本文の末尾に空行を 1 つ置いて原稿をそのまま加える。元の本文の執筆者の記載は書き換えない。
3. **添付を確かめる。** `nod doc show <Document id>` で kind=spec と対象 Issue へのリンクを確かめる。本文の指紋は、新規・作り直しなら `tail -n +3 <仕様書のパス> | shasum -a 256`、追記なら `tail -c <原稿のバイト数> <仕様書のパス> | shasum -a 256` が、`draft.sha256` に残した指紋と一致することを確かめる。
4. **決定ログに「執筆記録」の節を追記する。** 執筆の種類・日時・執筆者（実際のエージェントとモデル。追記では追記部分の執筆者）・原稿のファイル名と控えのディレクトリ名、作り直し・追記では改訂前の写しのファイル名を書く。
5. 3 を確認できたら、`nod issue update <id> --remove-label needs-spec` でラベルを外す。作成・更新・添付に失敗した場合や、仕様に未決事項が残る場合は外さない。解除に失敗したら、仕様 Document は保持し、失敗を報告してここで止める。
6. `nod issue update <id> --add-label ready-for-agent` でラベルを付ける。ラベルの定義が無くても付けられる。
7. `nod issue log <id> "<決定の要約と照合の経緯。執筆者（実際のエージェントとモデル。追記では追記部分の執筆者として）。決定ログの Document id>" --kind rationale` を 1 件残す。
8. Out of Scope に別 Issue へ切り出すものがあれば、ユーザーに確認してから `nod issue create ... --discovered-from <id>` で起票する。
9. `nod issue show <id>` で仕様 Document の添付と `needs-spec` がないことを確認し、完了を報告する。

- nod への書き込みはすべて主担当の書き手（`NOD_ACTOR`）で行う。
- 2 で仕様書を作成・書き換える前に失敗したら、再開するときは 1 からやり直す（止まっている間の入力の変化を見つけるため）。作成・書き換えた後に失敗したら、保存済みの原稿から失敗した手順の続きを再開し、執筆と 1 はやり直さない（作り直し・追記では対象をすでに書き換えているため）。

## 6. 完了時のネクストアクション

番号付きで示し、おすすめを 1 つ理由つきで添えて、ユーザーの選択を待つ（自分から次へ進まない）。

1. `nod:to-plan` で計画を立てる（おすすめ）
2. 仕様書を自分で読んでから進む
