# nod:backlog

要望を、単独で提供・検証できる Story に分解し、1 Story ごとに1 Issue を nod に起票する。
`pm-execution:write-stories` の Story、受け入れ条件、優先度、規模、依存関係をベースにする。このスキルだけで実行でき、元のスキルのインストールは不要。

引数は要望、会話の参照、PRD、仕様書、既存 Issue ID など。対象 Workspace・Project やテンプレート名の指定があれば使う。

## 1. 材料・起票先・依頼範囲を確認する

- `nod skills get nod` を読み、その手引きに従う。Codex では書き込み前に `export NOD_ACTOR=codex` を設定する。
- 会話と渡された資料から、対象者、困っている場面、実現したいこと、得られる価値を拾う。既存 Issue が指定されたら本文と関連 Document を読む。
- 起票先を確かめ、同じ要望の既存 Issue を探す。既存のものがあれば示し、新規作成か追記かが依頼から決まらない場合だけ確認する。
- 起票に必要な情報だけを確認する。未決事項を決定済みの仕様にせず、本文に残す。利用者への価値や完了条件を定義できない場合は、必要な質問をしてから起票する。
- 作成までの依頼か、下書き・相談だけの依頼かを確かめる。下書き・相談だけなら手順4で各 Story の本文と全体一覧を提示し、Issue を作成しない。承認済みの内容を改めて確認しない。

## 2. 要望を Story に分解する

- 要望に含まれる利用場面・操作・得られる価値を洗い出し、単独で提供でき、外から完了を確認できるまとまりを Story にする。複数の独立した価値があれば、複数の Story に分ける。
- 3 C's（短い要約・背景の説明・受け入れ条件）と INVEST（独立性・交渉可能性・価値・見積もり可能性・小ささ・検証可能性）で粒度を点検する。件数を先に決めず、5〜15件などの件数を満たすためだけに分割しない。分割不要な小さな要望は1件でよい。
- UI・API・DB など実装の層ごとに分けない。必要なエラー処理は、その振る舞いを提供する Story の受け入れ条件に含める。
- 各 Story の価値と完了条件を仮置きし、元の要望の抜けや重複を確認する。優先順・確定した依存関係・未決事項を整理し、単なる関連を依存にしない。

## 3. テンプレートを選ぶ

必ず `nod template list --json` で登録状況を調べる。

1. 登録済みなら `nod template show <名前>` で本文を読み、その見出し・順序・項目を使う。ユーザーが指定した名前を優先し、指定がなければ対象の用途に合うものを選ぶ。複数の候補から選べない、または登録済みのものがどれも用途に合わない場合は、候補を番号付きで列挙し、おすすめ1つと理由を示して確認する。
2. 一覧が空で、ユーザーによるテンプレートの明示指定もないときだけ、[標準テンプレート](assets/default-issue.md) を読んで使う。

テンプレートの登録・編集・削除は行わない。取得失敗や指定名が見つからない場合は「失敗時の扱い」に従う。
登録済みテンプレートに対応する欄がない情報は、関連する説明欄に収める。独自の見出しを足して標準テンプレートに作り替えない。

## 4. Story ごとに本文を作る

各 Story に選んだテンプレートを適用し、タイトル・Story・受け入れ条件を個別に作る。複数の Story を1つの本文にまとめない。
タイトルは、実現することが分かる短い日本語にする。

日本語の Story は、誰がどの場面で何をできるようになり、何が助かるかを自然な1〜2文で書く。主語が自明なら省き、対象者によって動作が異なる場合は明記する。
英語の「As a …, I want …, so that …」を逐語訳し、「利用者として」「それは〜のためだ」を定型句にしない。役割・機能・価値という情報は残す。

- 例：レポートをCSVで出力する際に必要な列だけを選び、出力後に不要な列を手で削除する手間を省けるようにする。
- 対象者が重要な例：管理者が退職者のアクセス権をまとめて無効化できるようにし、解除漏れを防ぐ。

受け入れ条件は外から確認できる結果をチェックボックスで書く。通常3〜5件を目安に、要望に必要な数にする。根拠のない仕様・性能値・デザインリンクは補わない。
優先度と規模は、既知のものは記載し、推奨は「案」、判断材料がなければ「未定」とする。S/M/L を nod の数値 estimate に機械変換しない。

共通の技術的注意点は必要な Issue の背景・補足に記載し、推測の実装計画を追加しない。
下書きのみの場合も、各 Story の本文に加えて手順6と同じ全体一覧を返す。Issue ID の代わりに仮番号を使う。

## 5. 1 Story ごとに1 Issue を起票する

- 手順1で作成まで依頼されていることを確認できた場合に、整理できた Story から個別に起票する。各 Story に対して以下の作成・本文反映を繰り返し、Story と返った Issue ID の対応を保持する。
- ユーザーに依頼された起票には `--requested` を付ける。Workspace・Project・親子関係・優先度・依存関係は依頼または確認できた内容だけを反映し、独自に Cycle や担当を割り当てない。Story 一覧の P0（最優先）と nod の 0（優先度なし）は意味が異なるため、数値をそのまま渡さず `nod issue create --help` の意味に合わせる。
- 登録済みテンプレートを使うときは `nod issue create "<タイトル>" --template "<名前>" --requested --json` で作成し、返った ID に対して `nod issue update <id> -d "<空欄を埋めた本文>"` を実行する。`--template` と `-d` は同時に渡せない。
- 標準テンプレートの場合は `nod issue create "<タイトル>" -d "<完成した本文>" --requested --json` を使う。本文は構造化引数か安全に引用した引数で渡し、シェルに本文中の記号を実行させない。
- 必要なオプションは上記のコマンドに追加する。依存先から作り、確定したブロック関係は `nod issue relate <先に終えるID> --blocks <待つID>` で記録する。単なる関連や未確認の依存をブロック関係にしない。

## 6. 各 Issue を再取得し、全体一覧で報告する

作成したすべての Issue を `nod issue show <id> --json` で再取得し、本文・起票先・関係を確認する。各 Story が1件の Issue に対応し、それぞれに受け入れ条件と選んだテンプレートが適用されていることを確かめる。

Story 全体を、優先順・Issue ID・タイトル・使用テンプレート・依存先・未決事項が分かる一覧で報告する。優先順が未確定なら「案」または「未定」とし、並び順だけで確定扱いにしない。依存先は分かる Issue ID で示し、ない場合は「なし」、未確認なら「未確認」とする。作成や本文更新が未完了の Story があれば、一覧にその状態も残す。
実装や仕様書・計画の作成は、別途依頼されていれば進める。

## 失敗時の扱い

- テンプレートの取得失敗を「未登録」と扱わない。取得できなかったことを報告し、標準テンプレートへ切り替えない。
- 指定したテンプレートが見つからないときも標準テンプレートへ切り替えず、指定名を確認する。
- 作成後の本文更新が失敗したら、その ID と未完了の更新を報告し、同じ Issue を作り直さない。
- 応答が失われて作成の成否が不明なら、一覧や本文で照合してから再試行する。
