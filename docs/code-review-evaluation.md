# コードレビューの評価用データセット

`nod:code-review` の検出性能が落ちていないかを、固定した過去の事例で確かめるための常設データセットと、その運用手順をまとめる。
評価は CLI を使わず、評価を担う親のセッションが、通常のレビューと同じ3担当への委譲を[親の手順](../plugins/nod/skills/code-review/references/parent.md)で行う。専用のモデル起動・採点の CLI は作らない。担当の定義とロールの配置は[コードレビュー担当エージェントの配置](code-review-agents.md)を参照。

## 置き場所と構成

`~/.local/share/nod/review-evaluation/`（nod のデータディレクトリ配下）に置く。正解がレビューの入力や対象の commit に混ざらないよう、どの Git リポジトリにも入れない。

| 場所 | 区分 | 内容 |
|---|---|---|
| `inputs/<case-id>/` | レビュー入力 | `case.md`（対象リポジトリの絶対パス、基点の指定、merge-base と head の40桁の SHA、mode、要求の写しの一覧、当時の要求の出典と復元の限界）、`requirements/`（当時の要求の原文の写し）、`standards/`（Git 管理外の当時の規約の写しがあるときだけ）、`manifest.md`（各ファイルの sha256） |
| `oracle/<case-id>.md` | 判定者用資料 | 原因 ID ごとの種類（正例／対照）、重大か、期待判定、原因と到達条件、影響、出典、裏付け（実行 probe・修正 commit・再確認）、実装モデルとその出典、使用履歴、人の確認記録 |
| `sets/v<N>.md` | 集合の定義 | 事例と原因の一覧、開発用／評価用の区分、採用版（基準）、比較の構成名、`inputs/`・`oracle/` の指紋、変更履歴 |
| `runs/<run-id>/` | 実行記録 | 全担当の原出力、状態、構成、所要時間、使用量、指摘と原因の対応、人の確定（書式は `runs/README.md`） |

- `inputs/` の要求は、通常のレビューと同じ範囲（Issue 本文、`kind=spec` の Document、計画の出典が指す Document、Git 管理外の Workspace の規約）の当時の版を写す。リポジトリ内の規約は写さず、担当が固定 SHA から読む。
- `inputs/` には、正解、過去のレビュー、修正の解説、PR の本文、後の修正コード、PR の番号・URL（過去のレビューへたどれる）を入れない。
- `inputs/<case-id>/` は通常のレビューの `input/` へそのまま写せる形にする（`case.md` が `target.md`、`requirements/` が `requirements/` に対応する）。

### レビュー担当に読ませない

- 評価用ディレクトリのパスも、`oracle/`・`sets/`・`runs/` の中身も、レビュー担当の依頼本文・共通の context・入力に入れない。担当には、通常の作業ディレクトリへ写した `input/` だけを渡す。
- 担当が評価用ディレクトリ、固定 SHA 以外の commit（後の修正 commit など）、過去のレビューの記録を読んだ実行は、有効な結果として扱わない。観測が足りず有無を確かめられない場合も同じ。

## 事例の追加

マージ後に不具合が見つかるたびに、候補として登録する。

1. 原因を作り込んだ PR の base（merge-base）と head の SHA を固定して `inputs/<case-id>/case.md` に書く。`git -C <repo> cat-file -e <SHA>^{commit}` で読めることを確かめ、結果を書く。
2. その時点の要求を `inputs/<case-id>/requirements/` に丸ごと写す。後で変わった要求は当時の版を写し、復元できない部分と理由を `case.md` に書く。各ファイルの sha256 を `manifest.md` に書く。
3. `oracle/<case-id>.md` に、原因 ID、種類、重大か（下の「重大の基準」で決める）、期待判定、原因と到達条件、影響、出典、裏付け（修正 commit、再現の probe、再確認）、実装モデルとその出典、使用履歴を書く。人の確認記録は「未確認（候補）」にする。
4. 開発用か評価用かを登録時に決め（下の分離の規則に従う）、区分と理由を新しい版の `sets/` に記録する。
5. 出典と裏付けを利用者に示し、利用者が確認した原因だけを正式な正解にする（人の確認記録に日付と確認した内容を書く）。区分は採用時にも確かめて記録する。人の確認前の候補は、確定した正解の分母に入れない。

集合を変えたとき（事例の追加・除外、正解の確定、区分の変更）は、新しい版の `sets/v<N+1>.md` を作り、前の版は残す。

### 重大の基準

重大は、[Greptile の Severity Badges](https://www.greptile.com/docs/code-review/first-pr-review)（P0 Critical / P1 High / P2 Medium）の P0 の定義に当たる影響（セキュリティの脆弱性・データ消失・クラッシュ／主要機能の停止）とする。元のレビューのバッジやラベルではなく、影響の中身で決める。それ以外の誤動作・境界条件の不具合（P1 相当以下）は重大でないとする。区分は他の項目と同じく利用者の確認で確定する。

## 開発用と評価用の分離

- スキルやエージェント定義を直すときに、中身や結果を見てよいのは開発用だけとする。評価用の中身と事例ごとの結果は、直す作業に使わない。利用者へは、評価用について原因ごとの合否と差を報告する。
- 開発用と評価用に、同じ PR、同じ原因、近接した派生事例（同じ PR の別の head、積み重ねた PR、同じ原因を別の版で再現した事例など）をまたがせない。
- 区分は登録・採用時に決めて記録する。後から変えるのは、評価結果を見てスキルや定義を直した事例を評価用から開発用へ移す場合だけとする。移すときは `sets/` の変更履歴に日付・理由・使った実行を残し、その事例をそれ以後「未使用の評価事例」と呼ばない。
- 初期の集合では、評価用に対照（誤指摘しやすいが正しい実装）が無い。評価用では対照の誤検出の比較ができないため、事例を足すときは評価用の対照を増やす。

## 再評価

`code-review` スキル、レビュー担当の定義、ロールのモデル設定のどれかを変えたら、通常運用へ採用する前に再評価する。開発用の事例は直す作業の確認に使ってよいが、再評価の合否は評価用の全事例で決める。

1. 準備: `runs/<run-id>/run.md` に目的・集合の版・基準（直前に利用者が受け入れた採用版）を、`configs.md` に新しい構成（スキルの commit、3定義の本文の sha256、ロールのモデル設定）を書く。実装モデルと比較用のモデルが重なる事例と、実装モデルが未確認の事例は外し、理由を書く。
2. 実行: 評価用の全事例に、新しい構成を1回ずつ実行する。事例ごとに次を行う。
   - 親の手順の2節と同じく作業ディレクトリを作り、`inputs/<case-id>/case.md` を `input/target.md` へ、`requirements/`（と `standards/` の中身）を `input/requirements/` へ写す。写した sha256 が `inputs/<case-id>/manifest.md` と一致することを確かめてから `input/manifest.md` を作る。nod から要求を取り直さない。
   - 親の手順の4〜8節のとおり、Standards 探索と Spec 探索を並列に委譲し、検査の後に反証を委譲し、最終状態と点数を決める。8節の要求の取り直しは、nod ではなく `inputs/<case-id>/` と比べる。
   - 報告は `parent/report.md` までにし、nod の Document・作業ログには保存しない（過去の Issue に書き込まない）。親の手順の3節のテスト実行は比較に使わないので省いてよく、省いたことを記録する。
   - 全担当の原出力、状態、使用量、所要時間を `runs/<run-id>/<case-id>/<構成名>/` に残す。
3. 照合: 実行者は、反証後の要対応（反証で追加した発見を含む）と判定者用資料の既知原因・対照との対応を、根拠（場所・到達条件・破綻の一致）付きで仮判定する。
4. 確定: 構成名を伏せた一覧を利用者に示し、利用者が対応を確定する。
5. 判定: 直前の採用版と、原因ごと・対照ごとに比べる。
   - 既知原因を原因ごとに見落とさない。基準で検出した原因を1件でも失えば不合格とし、合計の件数で相殺しない。新規の検出は改善として別に書く。
   - 対照の誤検出を、対照ごとに増やさない。
   - 新しい構成が未完了・未実施だった事例は、その事例の既知原因を見落としたものとして数える。
   - 既知原因の検出、重大原因（上の「重大の基準」による）の検出、対照の誤検出、完了率（分母は対象にした全事例）、担当ごとの使用量・所要時間を分けて報告する。
6. 採否: 利用者が受け入れたら、新しい構成を新しい基準として `sets/` の採用版に記録する。不合格または判定できない場合は変更を採らず、原因ごとの合否と差とともに利用者へ戻す。再実行するかは利用者が決め、最初の結果も残す。

## 初回の基準づくり

最初の基準は、新しいレビュー手順を採用する前の2段階比較で作る。① 現行版と新版を、3担当とも同じモデルにそろえて比べる。② 新版の探索の片方だけモデル設定を変えた構成を、① の新版と比べる。両段の結果を `runs/` に残し、利用者が受け入れた結果を最初の採用版として `sets/` に記録する。

## 記録

- 担当ごとに、トークン量（入力・出力・キャッシュの読み書き、取得できれば reasoning と合計）、担当 ID、実行状態、計測の出典、所要時間を記録する。取得できれば、実費、または単価の出典を付けた推計も記録する。旧版の実行は工程ごとに同じ項目を記録する。
- 欠測は `0` と書かず「取得できず」と書く。
- 使用量と費用は、費用上限などの合格値やレビューの点数には使わない。

## omp での使用量と構成の取り方

担当のセッション記録は `~/.omp/agent/sessions/<cwd>/<親セッション>/<担当ID>.jsonl` にある。`<cwd>` は親の作業ディレクトリをホームからの相対パスにして `/` を `-` に置き換えた名前（例: `~/repo/nod` は `-repo-nod`）、`<親セッション>` は親のセッションファイル名から拡張子を除いたもの。

```sh
S=~/.omp/agent/sessions/<cwd>/<親セッション>/<担当ID>.jsonl
# 使用量: assistant メッセージの usage を合計する
jq -s '[.[] | select(.type == "message" and .message.role == "assistant") | .message.usage]
  | {messages: length, input: (map(.input) | add), output: (map(.output) | add),
     cacheRead: (map(.cacheRead) | add), cacheWrite: (map(.cacheWrite) | add),
     totalTokens: (map(.totalTokens) | add)}' "$S"
# 構成: 起動時のロール・解決したモデル・ツールと依頼本文
jq -c 'select(.type == "session_init") | {modelRole, resolvedModel, tools, mountedTools, task}' "$S"
# 各メッセージのモデルと、フォールバックの有無
jq -c 'select(.type == "message" and .message.role == "assistant") | .message.model' "$S" | sort | uniq -c
jq -c 'select(.type == "model_change") | {model, resolvedModelIsFallback}' "$S"
# 所要時間: 最初と最後の記録の時刻
jq -r '.timestamp // empty' "$S" | sed -n '1p;$p'
```

- `usage` に reasoning の項目が無ければ「取得できず」と書く。
- `usage.cost` は omp が記録した値で、実費として扱わない。推計として使うときは単価の出典を書く。
- `resolvedModel`・`message.model` は設定の解決結果と申告であり、実効モデルの証明にはしない。
- 計測の出典として、記録ファイルのパスと sha256 を書く。

## 限界

- 1回ずつの比較で示せるのは、固定した集合での回帰の確認であり、統計的な性能の証明ではない。
- 比較用のモデルでの結果だけで、別の本番モデルの検出性能を確かめたとは扱わない。
- 正解は利用者が確認した時点の判断であり、対象に未知の不具合が無いことは示さない。対照はその主張についての対照であり、対象全体に不具合が無いことは示さない。
- 要求の写しは、当時の版を完全には復元できない場合がある（復元の限界は各 `case.md` に書く）。
- 評価用ディレクトリの分離と入力の写しは、アクセス遮断ではない。担当が読んだものは、実際の omp 経路の記録で確かめる。
