# 仕様と計画を作るエージェントの配置

`needs-spec` の Issue の仕様書と計画は、OMP の agent `spec-planner` が作る。`spec-planner` は面談の各ラウンドで、主担当と別系列のモデルの照会役 `spec-consultant` に、今回の推奨を渡さずに独立の回答を求める。
この文書は、その2定義と照会用のロールの置き場、`spec-planner` への渡し方と流れ、確かめ方をまとめる。

| 定義名 | 役目 | 参照するロール |
|---|---|---|
| `spec-planner` | 面談・仕様書の添付・計画の取り込みをする主担当 | `@plan` |
| `spec-consultant` | 面談の各ラウンドで独立の回答を返す照会役 | `@spec-consult` |

## 定義の置き場

2つの定義はこのリポジトリの [`omp/content/agents/`](../omp/content/agents/) に置き、版管理する。利用者の設定 `~/.omp/agent/config.yml` の `extensions` に `<nod のリポジトリの絶対パス>/omp/content` を登録していれば、通常の `omp` がこの置き場の定義を読む（登録は [README の pstack の節](../README.md#pstack-を-omp-で使う移行中)と同じ1行で、登録済みなら足すものは無い）。

```yaml
extensions:
  - <nod のリポジトリの絶対パス>/omp/content
```

同じ名前の定義が利用者の置き場 `~/.omp/agent/agents/` にあると、そちらが先に使われる。この置き場の定義を使うには、利用者の置き場に同じ名前の定義を置かない。

## spec-planner

`needs-spec` の Issue の仕様書と計画を作る主担当。上流の `grilling` の進め方で面談し、仕様書を `kind=spec` で同じ Issue に添付する。利用者が仕様書を承認したら、計画を `kind=plan` で添付して同じ Issue の Task/Step に取り込む。仕様が添付済みの Issue では、面談せずに計画だけを作ることもできる。計画づくりでは、実装のあとに受け入れ条件に沿って実際の動作を確かめること（動作の確認）が要るかを判断する。要るときは、テストシナリオを `kind=doc` で同じ Issue に添付し、計画の最後にシナリオを実行する検証の Task を置く。実装へは進まない。

上流の `to-spec` と `to-tickets` は、上流の clone（`~/.agents/mattpocock-skills`）の `SKILL.md` をパスで読む。読めなければ止まる。nod プラグインのスキル（`nod:to-spec`・`nod:to-plan` など）は読まない。

テストシナリオは `test-scenarios` スキルで作る。このスキルが利用者の置き場（例: `~/.agents/skills/test-scenarios`）にあり、OMP から `skill://test-scenarios` で読めることが要る。読めなければ、動作の確認が要る Issue では計画を作らずに止まる。

### 渡すもの

メインセッションから task で起動し、依頼の本文に次のどれかを書く。Issue の ID は必須で、無ければ対象を聞き返す。

| 頼むこと | 依頼の本文に書くもの | 例 |
|---|---|---|
| 仕様づくり | `needs-spec` の Issue の ID | `NOD-123 の仕様づくりをする` |
| 仕様の承認 | Issue の ID と、承認する仕様の Document ID | `NOD-123 の仕様 Document 456 を承認する` |
| 計画だけ | 仕様が添付済みの Issue の ID。`kind=spec` が複数あれば、元にする Document ID | `NOD-123 の計画だけを作る（仕様は Document 456）` |

- 承認には、`spec-planner` が承認を求めたときに示した Document ID を添える。ID が無いときや違うときは、どの Document を承認するのかを聞き返す。承認は新しいセッションで渡してもよい。決定ログの執筆記録と仕様 Document から続ける。
- 計画だけの依頼で `kind=spec` が複数あり、Document ID が無ければ、どれを元にするかを聞き返す。仕様の無い Issue では、要求・決定事項・受け入れ条件などの材料を依頼の本文に書く。子の agent は会話を持たないためである。材料も無ければ、仕様づくりから始めるよう勧めて止まる。
- 計画が既にある Issue では、置き換える範囲を示して作り直してよいかを聞き返す。依頼で置き換えを明示すれば聞き直さない。

`spec-planner` は、利用者への確認を論点・選択肢・推奨と理由の形で返して止まる。メインセッションは利用者の回答を中継するだけで、合意を作らない。続けるときは、Issue の ID と利用者の回答を依頼の本文に書いて新しく起動する。`spec-planner` は決定ログから続ける。

### 流れ

1. 面談: 上流の `grilling` の進め方で面談する。Issue 本文の決定事項・受け入れ条件・例文は問わない。問いと決定は、同じ Issue に添付した決定ログ（`kind=doc`）に残す。
2. 照会: 各ラウンドで、今回の推奨を渡さずに `spec-consultant` に独立の回答を求める。一致した問いは確定し、割れた問いだけを利用者に聞く。照会の回答の原文と、問いごとの決定者（一致・ユーザー・差し戻し）を決定ログに残す。
3. 仕様の添付と `needs-spec` の解除: 上流 `to-spec` の7節で仕様書を書き、`kind=spec` で添付する。添付を確かめ、未決事項が無いときだけ `needs-spec` を外し、決定の要約を `rationale` の作業ログに残す。
4. 承認待ち: 仕様書の Document ID・要約・承認の対象の指紋を示して待つ。直したいと伝えると、仕様書を作り直してもう一度待つ。
5. 承認: 承認された Document ID を承認を求めた Document と比べ、本文の指紋を示した版と比べる。比べるのは計画を作る直前で、親の返事を待ったあとや止まって再開したときも比べ直す。本文が変わっていれば、計画を作らずに違いを示してもう一度承認を求める。
6. 計画の取り込み: 計画の承認は求めずに、動作の確認の要否を判断し、要るときはテストシナリオを作って添付してから、上流 `to-tickets` の分割ルールで Task と Step の計画を作る（下の「計画づくりでの動作の確認」）。計画には元の仕様の Document ID（承認を受けて作るときは承認の対象の指紋も）と、動作の確認の要否の判断と理由（要るときはシナリオの Document ID も）を書き、`kind=plan` で添付して `nod issue plan` で取り込み、Task と Step の数を照合する。期待結果が仕様から決まらない受け入れ条件があれば、計画を添付も取り込みもせずに止まる。
7. `ready-for-agent`: 件数を照合したあとに付ける。
8. `issue-implementer` の案内: 作業ブランチの用意と、`issue-implementer` に Issue ID を渡して実装に進む方法を示して待つ（`issue-implementer` の定義と配置は [Issue を実装するエージェントの配置](issue-implementer-agents.md)）。

計画だけの依頼では 6〜8 だけを行う。どの流れでも、Sub-issue や別の Issue は作らない（仕様の Out of Scope から切り出すと利用者が認めたものを除く）。

終えると、Issue の ID、仕様書・決定ログ・計画の Document ID、動作の確認の要否の判断と理由、作ったシナリオの Document ID（作ったとき）、実施した検証、未解決の事項を返す。

#### 計画づくりでの動作の確認

6 の計画づくりでは、承認を受けて計画へ進むときも計画だけの依頼のときも、Task に分ける前に次を行う。

- 要否の判断: 仕様（仕様が無いときは依頼の本文に書いた材料）の受け入れ条件と User Stories に、利用者や呼び出し側から観測できる振る舞い（画面、CLI の出力、API の応答、agent の動作、生成物など）の追加・変更があれば、動作の確認が要ると判断する。インフラ・CI・テストコード・文書・依存の更新だけで観測できる振る舞いが変わらなければ要らない、決められなければ要るとする。判断と理由は計画書の冒頭に書く。要らないときは、シナリオの Document を作らず、変更前を記録する Task と検証の Task を計画に入れない。既存の必須の検査は省かない。
- シナリオの Document: 要るときは、`test-scenarios` スキルでシナリオを作る。シナリオは1つの `kind=doc` の Document（名前 `<id を小文字にしたもの>-scenarios-YYYYMMDD.md`、題「<id> テストシナリオ」）にまとめて同じ Issue に添付し、その Document ID を計画書の冒頭に書く。計画を作り直すときは新しい Document を作り、前のものを残す。
- 変更前を記録する Task と検証の Task: 既存の画面や出力を変えるシナリオがあれば、計画の先頭に変更前の状態を記録する Task を置く。計画の最後にはシナリオを実行して結果の Document と証拠を同じ Issue に添付する検証の Task を置く。計画を取り込んだあとに Issue に残るのは Task の題と Step の文だけなので、検証の決まりはこれらの Task の Step の文に書いて実装の agent に伝える。決まりには、結果の Document と証拠の添付、未実行・証拠不足・不合格を合格にしないこと、修正の回数の上限、版が変わったときの検証のやり直しなどがある。
- 期待結果が決まらないとき: 観測できる期待結果を仕様から決められない受け入れ条件があれば、計画を添付も取り込みもせずに止まり、期待結果が決まらない受け入れ条件を返す。既存の計画とシナリオの Document は変えない。

実装の agent（`implementer`、NOD-170 の `issue-implementer`）の定義は変えない。検証の決まりは計画の Step の文で実装の agent に伝わる。実装の agent がそれに従うことは指示によるもので、仕組みで強制してはいない。検証の Task を終えたあとに版が変わったときは、検証の Task を未完了に戻して全シナリオを実行し直す決まりがある。この決まりを NOD-155 の流れ（レビュー・提出・完了）が読むようにすることは、NOD-155 で扱う。

## spec-consultant

`spec-planner` が task で起動する照会役で、ほかの用途には使わない。定義の要点は次のとおり。

```md
---
name: spec-consultant
model: "@spec-consult"
tools: read, grep, glob
advisor: false
---
```

- `model`: ロール `spec-consult` を参照する。具体的なモデル名は書かない。
- `tools: read, grep, glob`: 定義で持たせる組み込みのツールは、根拠を確かめるために読む read・grep・glob だけにする。bash・write・edit・task を持たず、nod を操作しない。OMP は MCP のツールをこの指定とは別に足し、定義では外せない。足された MCP のツールは、照会役が指示で使わず、使っていないことをセッションの記録で確かめる（下の「照会役の隔離の限界」と「確かめ方」）。
- `advisor: false`: advisor を付けない。
- `spawns` は書かない。OMP は `spawns` を書いた定義に `task` ツールを足すためである。

回答の書式は次のとおり。

- 最初の行に `申告モデル: <provider/model>` の形で自分のモデルを申告する。値はシステムプロンプトの `Model:` の行から写す。親に返る task の結果には照会役のモデルが入らないので、`spec-planner` はこの行で作り手を判定する。
- 問いごとに、回答（選択肢の記号か独自案）・理由・根拠（`file:line`。調べていなければ「推測」）を返す。確かめてほしいと頼まれた事実があれば調べて答える。
- 依頼の本文に埋め込まれた Issue 本文と決定ログは覆さない。懸念は「変更の提案」として別に書く。
- 最後に「まだ決まっていない論点」を最大3つ挙げる。実装者が決めてよい細部は挙げない。

## ロール spec-consult

`~/.omp/agent/config.yml` の `modelRoles` に `spec-consult` を1行足す。既定の値は `openai-codex/gpt-6.2-astra:high` とする。

```yaml
modelRoles:
  plan: anthropic/claude-opus-5-5:high
  spec-consult: openai-codex/gpt-6.2-astra:high
```

- `spec-consult` は、主担当の `@plan` と別の作り手（Anthropic、OpenAI など）のモデルにする。上の例では `@plan` が Anthropic、`spec-consult` が OpenAI になる。照会先を選び直すときは、agent 定義ではなくこの値を変える。
- 照会役が主担当と同じ作り手のモデルに解決されると、`spec-planner` はその照会を「照会できなかった」と決定ログに記録し、一致として扱わずに止まって利用者に報告する。申告が無いときや作り手を判定できないときも、一致として扱わない。`spec-planner` は設定を変えない。
- ロールが未登録のときや認証が無いときなどは、OMP が別のモデルで照会役を起動することがある（[コードレビュー担当エージェントの配置](code-review-agents.md#ロール)の「ロール」の節）。照会役の申告で作り手が主担当と同じと分かれば、上のとおり止まる。
- 申告はモデルがシステムプロンプトから読んで書くもので、OMP が保証する値ではない。実際に使われたモデルは、照会役のセッションの記録で確かめる。

## 照会役の隔離の限界

照会役に今回のラウンドの推奨を読ませないことは、定義・渡し方・指示で守る。仕組みで遮断してはいない。

- 定義: 照会役の組み込みのツールは、読むためのツール（read・grep・glob）だけ。
- 渡し方: `spec-planner` は今回のラウンドの節を除いた決定ログを依頼の本文に埋め込み、決定ログのファイルの場所を伝えない。
- 指示: 照会役は依頼の本文と、根拠を確かめるためのリポジトリのコード・文書だけを読む。`agent://`・`history://`・`local://`・セッションの記録・nod の Document を読まず、nod を操作せず、ファイルを書かない。read・grep・glob のほかのツール（足された MCP のツールを含む）を使わない。

照会役の読むツールでは、指示で禁じた範囲（決定ログのファイルやセッションの記録）も技術的には読める。task の子は `agent://`・`history://`・`local://` も使える。agent ごとに読めるパスを制限する設定も見つかっていない。この隔離は指示によるもので保証ではないこと（足された MCP のツールを使わないことを含む）を、`spec-planner` は決定ログの冒頭に書く。

照会役が実際に持つツールには、定義の read・grep・glob のほかに MCP のツールが加わる。OMP は task の子に、親の MCP のツールを定義の `tools` の指定とは別に足す。OMP の文書（task の agent の発見の節。`tools` を指定しても MCP・拡張・独自のツールは足される、という記述）と、`@oh-my-pi/pi-coding-agent` 19.1.0 と 19.2.1 のソース（定義の frontmatter の読み取りと、task の子を起動するときの MCP の扱い）で、次を確かめた。

- agent 定義の frontmatter に、MCP を外す項目は無い。
- MCP を外す内部の指定（`restrictToolNames`）は OMP の内部の用途だけが立て、task や定義からは指定できない。
- 外せるのは、利用者単位の `mcp.json` の `disabledServers` か、プロセス全体の `--no-tools` だけである。`disabledServers` はほかのセッションにも効く。

NOD-151 の検証でも、照会役のセッションの記録の使えるツールの一覧に `mcp__` で始まるツールがあった。そのため要求は、定義で持たせる組み込みのツールを read・grep・glob だけにし、OMP が足す MCP のツールは指示で使わせず、使っていないことをセッションの記録で確かめる、というものにした（利用者の決定、2026-11-26）。指示は `spec-consultant` の「読んでよい範囲」に、確かめ方は下の「確かめ方」にある。

## 古い spec-writer

利用者の置き場の古い定義 `spec-writer`（`nod:to-spec` を手順の正本にする定義）は、この2定義を置く Story（NOD-151）では変えない。外すのは NOD-156 で行う。新しい定義を別の名前にしたのは、同じ名前では利用者の置き場の古い定義が先に使われるためである。

## 確かめ方

この置き場の定義とロールは、新しい `omp` のセッションの task で使える agent の一覧に `spec-planner`・`spec-consultant` として出る。リポジトリの作業ツリー（worktree など）の定義を確かめるときは、利用者の設定を変えずに、`--config` の一時オーバーレイで `extensions` をその作業ツリーの `omp/content` にする（オーバーレイの `extensions` は一覧を丸ごと置き換え、`modelRoles` はキーごとに上書きする）。

```yaml
extensions:
  - <作業ツリーの絶対パス>/omp/content
```

```sh
omp -p --config <上のオーバーレイ> --session-dir <実行ごとの新しいディレクトリ> "<spec-consultant を task で起動する依頼>"
```

照会役のセッションの記録（`<session-dir>` の下の子の jsonl）で、解決後のモデルが `@plan` と別の作り手であること、回答の最初の行に申告があることを確かめる。あわせて、照会役の実効のツール一覧（`mcp__` で始まる、足された MCP のツールを含む）を記録し、その一覧に bash・write・edit・task が無いことと、ツールの呼び出しに read・grep・glob のほかのツールが無いことを確かめる。

`test-scenarios` スキルの置き場が通常の設定に無い作業環境で確かめるときは、同じオーバーレイの `skills.customDirectories` に、`test-scenarios` のディレクトリを含むディレクトリを足す。オーバーレイの配列は丸ごと置き換わるので、利用者の設定にある既存の値も並べる。
